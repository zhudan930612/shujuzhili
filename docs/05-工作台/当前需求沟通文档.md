## 需求沟通专题：行政区域层级与辖区权限

### 背景诉求
- 后续平台可能在不同省、市、区开展业务，当前项目、巡查、法规库尚未形成统一行政区域或辖区管理口径。
- 业务上存在“巡查人员只能看到自己辖区内项目数据”的诉求，同时不同地区可能存在不同法规、标准或监管要求。
- 本专题处于需求沟通阶段；当前已确认先只涉及后台管理系统，结论稳定后再拆回项目管理、巡查员账号、后台巡查管理、法规库和法规匹配相关正式文档。

### 增加行政区域划分的原因
- 支撑跨地区业务开展：项目后续会分布在不同省、市、区，如果缺少行政区域归属，后台项目、巡查记录和法规数据会混在同一数据池，难以按地区管理。
- 支撑辖区数据权限：巡查员账号需要按负责辖区查看项目和巡查数据，行政区域是判断“哪些项目属于该账号可见范围”的基础条件。
- 支撑地方化法规引用：不同地区可能有本地安全监管要求或地方标准，法规库需要用适用地区区分全国通用法规与地方适用法规。
- 支撑后台查询与运营统计：项目管理、后台巡查管理和法规库都需要按地区筛选，便于运营人员按区域排查数据、统计工作量和发现缺口。
- 降低后续返工风险：先建立项目属地、账号辖区、法规适用地区的统一口径，后续扩展移动端、报表或跨区协作时可复用，不需要重新改造底层规则。

### 业务场景与需求
| 场景 | 业务描述 | 对应需求 |
|------|----------|----------|
| 多地区开展业务 | 平台后续可能在不同省、市、区开展安责险事故预防服务 | 平台需要识别项目所属行政区域，避免所有项目混在全局项目池 |
| 项目来自不同备案系统 | 不同地区可能有自己的备案系统或项目来源口径 | 项目主数据需要记录项目属地、来源系统和同步来源，便于追溯 |
| 巡查员只负责指定辖区 | 巡查员只负责某个区或多个区的项目 | 巡查员账号需要绑定可见辖区，后台项目选择与数据查看按辖区过滤 |
| 区级/市级管理人员查看辖区数据 | 区级管理员看本区，市级管理员看全市 | 后台需要支持区域级数据权限 |
| 平台运营查看全量数据 | 平台管理员或总部运营需要跨区域查看、统计和配置 | 需要保留全局管理员权限 |
| 巡查记录按项目归属隔离 | 巡查记录是项目产生的数据 | 巡查记录默认从项目继承区域权限，不单独维护区域 |
| 后台上传巡查记录 | 后台人员手动上传巡查记录时选择项目 | 上传页选择项目范围需要按当前账号可见辖区过滤 |
| 巡查记录详情纠错 | 详情页编辑关联项目时可能改到其他项目 | 编辑态项目选择范围同样受辖区权限限制 |
| 后续移动端扫码进入项目 | 巡查员可能通过二维码或项目编号进入项目 | 移动端后续单独评估，扫码或搜索后仍需校验项目是否在账号可见辖区内 |
| 跨区临时支援 | 巡查员临时支援其他区项目 | 账号需要支持绑定多个辖区；临时授权可后续扩展 |
| 法规存在地方差异 | 不同省、市、区可能有不同地方标准或监管要求 | 法规库需要增加适用地区，支持全国、省、市、区等层级 |
| 隐患识别/报告引用法规 | 同一隐患在不同地区可能引用不同法规依据 | 法规匹配应优先匹配项目所在地法规，再回退上级或全国法规 |
| 统计分析按区域汇总 | 管理层需要看各区项目数、巡查完成率和隐患量 | 报表和列表筛选需要支持行政区域维度 |
| 数据迁移和历史数据 | 现有项目可能没有区域字段 | 需要定义历史项目区域补录或默认归属规则 |
| 区域调整 | 行政区划或业务辖区可能变化 | 区域字典需要启停、层级维护，被引用后不能随意删除 |
| 保险公司/服务机构分工 | 部分数据可能还要按保险公司或服务机构隔离 | 权限模型需预留“区域 + 机构”的组合能力 |

### 需求拆分
| 需求类别 | 核心需求 | 说明 |
|----------|----------|------|
| 区域基础数据 | 建立统一行政区域字典 | 作为项目、账号、法规共同引用的唯一来源 |
| 项目属地 | 项目新增、导入、同步时记录所属行政区域 | 项目是区域权限和法规匹配的基础 |

### 行政区域层级口径
- 本阶段行政区域层级确定到街镇一级，采用“省 / 市 / 区县 / 街镇”四级结构。
- 项目所属行政区域尽量选择到街镇；若仅能确认到上级层级，页面通过提示文案引导用户补充，不做强阻断。
- 巡查员账号的可见辖区、后台巡查管理的区域筛选沿用到街镇一级；法规库适用地区只到区县一级，不支持街镇。

### 项目管理功能设计沟通

#### 行政区域字段位置
- 新增项目弹窗中，`行政区域` 放在 `项目地址` 后方展示。
- 推荐录入顺序为：`项目名称 → 施工类型 → 项目地址 → 行政区域 → 施工时间 → 关联保险公司 → 施工单位 → 负责人姓名/电话 → 备注`。
- 原因：项目地址大概率来自批量导入或外部项目数据，行政区域优先根据项目地址解析到省/市/区县，再由人工选择街镇；把行政区域放在项目地址之后，更符合“先有地址，再解析三级，再补全街镇”的操作路径。

#### 项目地址与行政区域生成规则
| 场景 | 规则 |
|------|------|
| 批量导入项目 | 根据 `项目地址` 自动解析到省/市/区县，街镇由人工选择 |
| 新增项目 | 用户输入项目地址并离开项目地址输入框后触发解析；解析期间行政区域不可选择 |
| 编辑项目 | 项目地址沿用现有规则保持只读；行政区域允许修改，用于纠正地址解析或导入后的区域归属错误 |
| 解析成功 | 返回并显示行政区域内容；若仅解析到区县，则街镇下拉按区县加载并允许选择 |
| 解析不完整 | 解析到哪一级就从哪一级开始手动选择；同时不限制用户调整已解析出的上级层级 |
| 解析失败 | toast 提示“行政区域解析失败，请手动选择”，随后允许用户手动选择行政区域 |
| 人工选择街镇 | 运营人员在解析出的区县下选择街镇，选择结果作为项目最终行政区域 |

#### 初步规则
- `项目地址` 仍为必填字段。
- 批量导入模板不新增行政区域字段；`行政区域` 不要求导入文件手工填写，系统根据项目地址自动解析到省/市/区县。
- 街镇不依赖自动解析，默认显示“请选择”，由运营人员人工选择。
- 新增项目时，系统在项目地址输入框失去焦点后触发行政区域解析；解析过程中行政区域控件不可选择。
- 解析成功后，行政区域控件展示返回的省/市/区县，街镇默认显示“请选择”，并允许继续选择或修正街镇。
- 行政区域为必填项，字段下方提示“请尽量选择到对应的街镇层级”。
- 解析失败时，toast 提示“行政区域解析失败，请手动选择”，然后开放行政区域手动选择。
- 导入预览必须展示解析出的省/市/区县，并提供街镇选择入口。
- 只解析到省/市或完全无法解析时，标记为“需手动补充行政区域”；手动选择时从已解析层级继续选择，同时允许调整已解析出的上级层级。
- 用户可在新增项目和编辑项目时手动调整行政区域；人工选择或修正后的行政区域优先级高于自动解析结果。
- 项目管理列表页仅增加行政区域筛选条件，不在列表字段中新增行政区域列。
- 项目详情页需要展示项目所属行政区域。
- 项目编辑态允许修改行政区域，项目地址仍按现有规则保持只读。
- 项目行政区域修改后，按项目最新归属影响后续筛选、权限过滤和法规匹配。

#### 地址解析实现候选
- 两个候选方案的业务本质一致：都通过 `项目地址` 解析行政区划，将解析出的省/市/区县填入对应字段；用户仍可在导入预览、新增或编辑场景中进行手动调整。
- 手动调整结果优先级高于自动解析结果，最终保存时以用户确认后的标准行政区域为准。

| 方案 | 定位 | 使用边界 |
|------|------|----------|
| 方案一：GitHub 开源库 `shibing624/addressparser` | 离线解析候选，用于从项目地址中提取省/市/区县 | 该方案主要面向省/市/区三级解析，不承担街镇级最终判定；可作为天地图不可用时的备选方案 |
| 方案二：天地图地理编码服务 | 优先评估的在线 API 方案，使用天地图地址地理编码与逆地理编码能力辅助解析项目地址 | 需评估接口 Key、调用配额、网络稳定性、隐私合规、批量导入吞吐，以及返回字段能否稳定支撑省/市/区县识别 |

- 方案一参考：[shibing624/addressparser](https://github.com/shibing624/addressparser)
- 方案二参考：[天地图地理编码接口](http://lbs.tianditu.gov.cn/server/geocodinginterface.html)、[天地图逆地理编码接口](http://lbs.tianditu.gov.cn/server/geocoding.html)
- 若采用 `shibing624/addressparser`，系统仍需将解析结果映射到平台统一行政区划库，最终保存标准区域编码和完整路径。
- 若采用天地图服务，建议按“项目地址 → 地理编码获取坐标 → 逆地理编码获取结构化行政区划 → 映射平台行政区划库”的流程验证；最终仍以平台标准区域编码和完整路径作为保存结果。
- 若三级解析失败或结果存在歧义，导入预览标记为“需手动补充行政区域”，不直接导入。

### 巡查员账号功能设计沟通

#### 服务区域字段口径
- 当前系统巡查员账号中已存在 `服务区域` 字段，后续复用该字段承接可见辖区配置，不新增平行字段。
- 文档口径：`服务区域 = 巡查员可见辖区 = 后台数据权限范围`。
- `服务区域` 继续复用现有级联多选组件，支持按行政区域层级选择。

#### 服务区域选择规则
| 规则项 | 说明 |
|--------|------|
| 是否必填 | 巡查员账号必填 |
| 选择方式 | 级联多选 |
| 支持层级 | 省 / 市 / 区县 / 街镇 |
| 选择上级区域 | 选择省、市、区县等上级区域时，默认包含其下级区域 |
| 多区域配置 | 支持一个巡查员绑定多个服务区域 |
| 街镇数据 | 如当前组件某些区县下暂无街镇数据，先按现有区域数据配置；后续区域数据补齐后继续沿用同一字段 |

#### 数据权限生效范围
| 应用位置 | 权限规则 |
|----------|----------|
| 项目管理 | 巡查员仅能查看服务区域内的项目 |
| 后台上传巡查记录 | 选择项目时，仅展示当前账号服务区域内的项目 |
| 后台巡查记录列表 | 仅展示服务区域内项目产生的巡查记录 |
| 巡查记录详情 | 巡查记录所属项目不在服务区域内时，不允许查看 |

#### 后续同步提醒
- 后续同步原型和 PRD 时，需检查巡查员账号新增/编辑弹窗中的 `所属单位` placeholder 是否存在复用错误；当前参考图中疑似显示为“请输入巡检人员名称”，应按字段语义修正。

#### 列表与详情展示边界

### 法规库功能设计沟通

#### 适用地区字段口径
- 法规库增加 `适用地区` 字段，用于表达法规条款适用于哪些行政区域。
- `适用地区` 是法规匹配和筛选字段，不作为账号数据权限字段。
- 适用地区默认值为 `全国`。
- 适用地区支持选择全国、省、市、区县任一层级，不支持街镇。
- 适用地区使用多级联动下拉控件；一级下拉第一个选项固定显示 `全国`。
- `全国` 与各省/直辖市同属一级选项，不作为各省/直辖市的父级。
- 用户选择 `全国` 时，不再继续展开下级区域；用户选择省、市时，再按层级联动展示下级区域；选择到区县后停止展开。

#### 列表与详情展示
- 法规库列表页增加 `适用地区` 筛选条件。
- 法规库列表字段中新增 `适用地区` 列。
- 法规详情页展示 `适用地区`。
- 新增/编辑法规时维护 `适用地区`。

#### 编辑适用地区规则
- 编辑法规时允许修改 `适用地区`。
- `适用地区` 变更后，仅影响后续法规匹配和新生成报告；历史已生成报告不自动更新。
- 已关联隐患的关联关系保留，后续匹配时按新的适用地区生效。
- 保存时不做二次确认，按普通编辑保存流程提交。

### 法规匹配功能设计沟通

#### 默认匹配规则
- 法规匹配依据为：`项目所属行政区域 + 隐患关联法规 + 法规适用地区`。
- 项目行政区域以项目最新所属行政区域为准。
- 法规适用地区以法规库当前启用法规的适用地区为准。
- 默认匹配按法规适用地区层级分层全部展示，优先级为：`区县 > 市 > 省 > 全国`。
- 同一层级命中多条法规时，全部展示。
- 不匹配项目所属行政区域路径的其他地区法规，默认不展示。
- 停用法规不参与后续新匹配。
- 已生成报告不因后续法规适用地区调整而自动更新。

#### 分层展示示例
```text
项目：广东省 / 深圳市 / 南山区 / 粤海街道
隐患：临边防护缺失

默认展示：
1. 南山区适用法规
2. 深圳市适用法规
3. 广东省适用法规
4. 全国适用法规

默认不展示：
- 福田区适用法规
- 广州市适用法规
```

#### 人工选择其他适用地区
- 默认按项目所属行政区域路径分层展示法规，但用户可以切换或选择其他适用地区查看法规候选。
- 选择其他适用地区后，仅改变当前法规候选展示范围，不修改项目所属行政区域。
- 用户从其他适用地区选择法规时，应记录为人工选择结果，优先于默认匹配结果。
- 人工选择结果仅作用于当前业务结果或当前报告生成，不反向修改法规库适用地区。

#### 关联法规弹窗规则
- 关联法规弹窗打开时，应根据当前项目所属行政区域默认筛选法规的适用地区。
- 项目所属行政区域到街镇时，法规适用地区只匹配到区县层级，即默认展示该项目所在区县、市、省、全国适用法规。
- 关联法规弹窗只增加 `适用地区` 筛选条件和候选法规列表中的 `适用地区` 字段。
- 用户可通过 `适用地区` 筛选条件手动选择其他适用地区查看法规候选。
- 切换适用地区只影响弹窗候选法规，不修改项目所属行政区域，也不修改法规库中法规的适用地区。
- 默认不展示不在项目行政区域路径上的其他地区法规；例如南山区项目默认不展示福田区、广州市适用法规。
- 当项目所属行政区域为省/市/区县/街镇四级时，法规关联按省/市/区县三级适用地区匹配，街镇不参与法规适用地区匹配。
