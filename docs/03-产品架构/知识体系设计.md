# 数据治理平台知识库体系设计

> **文档定位**：定义支撑隐患识别报告输出的知识库结构，确保报告内容来自结构化知识库匹配，而非生成式AI自由生成。
> **设计原则**：从最终输出结果倒推知识库设计，确保每个输出字段都有明确的数据来源。
> **版本**：v1.0
> **更新日期**：2026-03-23

---

## 0. 文档职责边界

- 本文档负责知识结构、编码体系、维护原则和长期边界。
- 知识库后台页面的字段、状态、交互规则唯一来源在 [后台管理/知识库管理.md](后台管理/知识库管理.md) 的页面章节。

## 1. 设计背景与约束

### 1.1 产品约束
- **AI职责边界**：AI负责隐患识别；法规依据与整改建议由结构化知识库匹配；生产报告文本不由生成式AI自由生成。

### 1.2 设计目标
- 建立结构化知识库体系，支撑隐患识别报告的自动化生成
- 确保报告内容的专业性、准确性和可追溯性
- 支持知识库的持续维护和迭代

```

发现隐患：

   - 隐患等级：重大

   - 整改建议：加高栏杆至1.2m以上，确保横杆符合要求

     一名工人从4楼坠落身亡。（来源：XX市应急管理局事故通报）

2. 洞口未设置防护
   - 隐患描述：洞口未设置盖板或防护栏杆
   - 位置：[照片中的框选区域]
   - 隐患等级：重大
   - 法规依据：《建筑施工高处作业安全技术规范》JGJ80-2016 第4.2.1条
   - 整改建议：根据洞口尺寸采取盖板或栏杆防护措施，盖板需固定牢固
```

## 4. 知识库详细设计

### 4.1 隐患库（4级结构）

**用途**：定义所有可识别的隐患类型及其标准化描述，采用4级分类结构，是知识库体系的核心。

**分级说明（嵌套关系）**：

四级分类采用**嵌套层级结构**，每一级都是上一级的细化维度：

- **一级：行业域** - 隐患所属的行业领域（如建筑施工、危险化学品等）
- **二级：事故类型** - 在行业域内，按照事故分类标准划分的大类（如高坠、物体打击、机械伤害、触电、坍塌等）
- **三级：检查点位** - 在特定事故类型下，具体的检查位置类型（如临边洞口、脚手架、基坑边坡等）。检查点位代码在同一行业域+事故类型组合内唯一。
- **四级：具体隐患** - 在特定检查点位下，最细粒度的隐患类型，AI识别的目标（如防护栏杆高度不足、防护栏杆缺少踢脚板等）

**为什么采用嵌套而非并列**

1. **业务语义准确**：同类隐患在不同检查点位上，整改工艺和验收标准可能完全不同（如临边栏杆和脚手架栏杆的高度要求）
2. **符合专家维护习惯**：建筑专家整理隐患的思维路径是"事故类型→检查位置→具体隐患"，与现场巡查流程一致
3. **整改措施精准绑定**：每个隐患实体绑定明确的整改措施，无需运行时根据上下文动态适配

**包含信息**：

| 字段名称 | 字段描述 | 示例内容 |
|---------|---------|---------|
| 隐患编码 | 唯一标识，包含4级层级信息 | JZ-FALL-EDGE-0001 |
| 行业域 | 隐患所属的行业领域（一级），取值为行业域代码（不含ALL） | JZ（建筑施工） |
| 一级分类（事故类型） | 隐患所属的事故大类（二级） | 高坠 |
| 二级分类（检查点位） | 隐患发生的具体位置类型（三级） | 临边洞口 |
| 隐患名称 | 隐患的简短名称（四级） | 防护栏杆高度不足 |
| 隐患描述 | 标准化的隐患描述，用于报告输出 | 防护栏杆高度不足（低于1.2m） |
| 隐患等级 | 隐患的严重程度 | 重大、较大、一般 |
| 关联法规IDs | 适用的法规条款ID列表 | JZ-JGJ-0001,ALL-GB-0002 |
| 整改措施 | 标准化的整改操作步骤 | 加高栏杆至1.2m以上，确保横杆符合要求 |
| 整改期限 | 整改的紧急程度，固定选项 | 立即整改、限期整改 |
| 创建时间 | 该隐患类型首次录入的时间 | 2026-03-23 10:00:00 |
| 更新时间 | 最后一次修改的时间 | 2026-03-23 10:00:00 |
| 创建人 | 录入该隐患类型的人员 | 张三 |
| 更新人 | 最后修改的人员 | 张三 |
| 状态 | 该隐患类型是否在使用中 | 启用、停用 |
| 备注 | 其他需要说明的信息 | - |

**编码规则说明**：
```
JZ-FALL-EDGE-0001
 │    │     │     └─ 四级：具体隐患序号（自增四位数字，行业域内唯一）
 │    │     └─────── 三级：检查点位代码
 │    └───────────── 二级：事故类型代码
 └────────────────── 一级：行业域代码

常用代码：
- 行业域：JZ(建筑施工)、WH(危险化学品)、JT(交通运输)、YL(金属冶炼)等
- 事故类型：FALL(高坠)、STRIKE(物体打击)、MECH(机械伤害)、ELEC(触电)、COLLAPSE(坍塌)
- 检查点位：EDGE(临边洞口)、SCAFFOLD(脚手架)、PIT(基坑边坡)、ELECBOX(配电箱)

编码规则（体现嵌套层级）：
- 一级（行业域）：统一采用两字母简称，全局唯一
- 二级（事故类型）：在各行业域内自定义字母编码，同一行业域内唯一
- 三级（检查点位）：在各事故类型下自定义字母编码，同一行业域+事故类型组合内唯一
- 四级（具体隐患）：采用自增四位数字编码，每个行业域独立维护自增序列

**检查点位编码的嵌套特性说明**：检查点位代码（如 EDGE、SCAFFOLD）不是全局唯一的，而是在特定事故类型下定义。例如"临边洞口"在高坠事故中有一个代码，在其他事故类型中可能另有定义，或不存在。这种设计保证了编码的层级归属清晰，也便于各行业根据实际需要灵活组织检查点位。
- 隐患删除时标记为「停用」，该编码永久废弃不复用，确保历史报告可追溯
```

**示例**：

```
隐患编码：JZ-FALL-EDGE-0001
行业域：JZ（建筑施工）
一级分类（事故类型）：高坠
二级分类（检查点位）：临边洞口
隐患名称：防护栏杆高度不足
隐患描述：防护栏杆高度不足（低于1.2m）
隐患等级：重大
关联法规IDs：JZ-JGJ-0001,ALL-GB-0002
整改措施：加高栏杆至1.2m以上，确保横杆符合要求
整改期限：立即整改
创建时间：2026-03-23 10:00:00
更新时间：2026-03-23 10:00:00
创建人：张三
更新人：张三
状态：启用
备注：-
```

**4级结构示例**（建筑施工-高坠类）：

```
建筑施工 JZ（一级：行业域）
├── 高坠 FALL（二级：事故类型）
│   ├── 临边洞口 EDGE（三级：检查点位）
│   │   ├── JZ-FALL-EDGE-0001：临边未设置防护栏杆（四级）
│   │   ├── JZ-FALL-EDGE-0002：防护栏杆高度不足（四级）
│   │   ├── JZ-FALL-EDGE-0003：防护栏杆缺少踢脚板（四级）
│   │   ├── JZ-FALL-EDGE-0004：防护栏杆不牢固（四级）
│   │   ├── JZ-FALL-EDGE-0005：洞口未设置防护（四级）

│   ├── 脚手架 SCAFFOLD（三级）
```

### 4.2 法律法规库（法规条款库）

**用途**：存储法规条款，为隐患识别提供法规依据。

**包含信息**：

| 字段名称 | 字段描述 | 示例内容 |
|---------|---------|---------|
| 条款ID | 系统内部唯一标识 | JZ-JGJ-0001 |
| 适用行业 | 法规适用的行业领域（单选） | JZ（建筑施工）、ALL（通用） |
| 法规名称 | 法规的完整名称 | 建筑施工高处作业安全技术规范 |
| 法规编号 | 法规的官方编号 | JGJ80-2016 |
| 条款编号 | 具体条款的编号 | 第3.0.2条 |
| 条款内容 | 条款的完整文字内容 | 高处作业人员必须按规定正确佩戴安全带，安全带应高挂低用，挂点应牢固可靠 |
| 法规类型 | 法规的级别分类 | 国家标准、行业标准、地方标准、企业标准 |
| 状态 | 该法规是否仍在使用 | 启用、停用 |
| 创建时间 | 该条款首次录入的时间 | 2026-03-23 10:00:00 |
| 更新时间 | 最后一次修改的时间 | 2026-03-23 10:00:00 |
| 创建人 | 录入该条款的人员 | 张三 |
| 更新人 | 最后修改的人员 | 张三 |



**编码规则说明**：
```
JZ-JGJ-0001
 │   │    └─ 四位自增序号（各类型独立维护，删除后不复用）
 │   └───── 法规类型代码
 └───────── 行业编码（或 ALL 表示通用）

法规类型代码：
- GB：国家标准
- HB：行业标准
- DB：地方标准
- QY：企业标准
- QT：其他

行业编码：
- 与隐患库行业域两字母代码一致：JZ、WH、JT、YL 等（详见附录 8.1 行业域代码）
- 增加 ALL（通用）：仅法规库可用，表示适用于所有行业的法规
```

**示例：JGJ80-2016 第4.1.2条**

```
条款ID：JZ-HB-0001
适用行业：JZ（建筑施工）
法规名称：建筑施工高处作业安全技术规范
法规编号：JGJ80-2016
条款编号：第4.1.2条
条款内容：防护栏杆高度不得低于1.2m，立柱间距不大于2m，并设置水平横杆和踢脚板
法规类型：行业标准
创建时间：2026-03-23 10:00:00
更新时间：2026-03-23 10:00:00
创建人：张三
更新人：张三
状态：启用
```

### 4.3 隐患案例库

**用途**：存储真实发生的灾害事故案例，与隐患类型关联，在报告中展示用于警示教育，让相关人员认识到隐患的严重后果。

**包含信息**：

| 字段名称 | 字段描述 | 示例内容 |
|---------|---------|---------|
| 案例ID | 系统内部唯一标识 | CASE-001 |
| 隐患编码 | 关联的主要隐患编码（一个案例对应一个主要隐患） | FALL-EDGE-002 |
| 事故标题 | 事故的简短标题 | 某市某工地因防护栏杆高度不足致工人坠亡 |
| 事故摘要 | 事故经过的简要描述，用于报告输出 | 2024年6月，某市某建筑工地因临边防护栏杆高度不足，一名工人从4楼坠落身亡 |
| 事故后果 | 事故造成的人员伤亡情况 | 1人死亡 |
| 来源链接 | 原始信息的网址（如有） | https://... |
| 填充方式 | 案例的录入来源 | AI搜索、人工录入 |
| 创建时间 | 案例录入的时间 | 2026-03-23 10:00:00 |
| 更新时间 | 最后一次修改的时间 | 2026-03-23 10:00:00 |
| 创建人 | 录入该案例的人员 | 张三 |
| 更新人 | 最后修改的人员 | 张三 |
| 状态 | 该案例是否在使用中 | 启用、停用 |
| 备注 | 其他需要说明的信息 | - |

**案例库填充机制**：

- 隐患案例库支持外部填充与人工复核。
- AI 搜索、人工录入等仅作为案例内容的来源方式，具体填充流程不在本文展开。
- 未经审核启用的案例不会出现在报告输出中。

**示例**：

```
案例ID：CASE-001
隐患编码：FALL-EDGE-002
事故标题：某市某工地因防护栏杆高度不足致工人坠亡
事故摘要：2024年6月，某市某建筑工地因临边防护栏杆高度不足，一名工人从4楼坠落身亡
事故后果：1人死亡
来源链接：https://...
```

## 5. 知识库维护机制

### 5.1 知识库更新场景

| 场景 | 涉及知识库 | 触发条件 |
|------|-----------|---------|---------|
| 新增隐患类型 | 隐患库 | 标注过程中发现未覆盖的隐患类型 |
| 法规更新 | 法律法规库 | 法规条款修订或新增 |
| 法规废止 | 法律法规库 | 法规被新版本替代 |
| 整改方案优化 | 隐患库 | 实践中发现更优的整改方案 |
| 隐患描述优化 | 隐患库 | 描述不够准确或专业 |
| 新增隐患案例 | 隐患案例库 | 收集到新的真实事故案例 |

### 5.2 知识库回流机制

知识库回流流程以 [../02-业务流程.mmd](../02-业务流程.mmd) 为准，本文不复述 `P1-P5` 全流程。

从知识库结构设计视角，回流机制需要承接的结果包括：
- 支持新增隐患提报后的隐患库扩充。
- 支持审核通过后的知识库内容更新。
- 支持隐患库与法规库之间的同步维护。
- 支持口径版本发布/生效后对标注、质检、抽查口径的统一引用。

### 5.3 知识库版本管理

**版本控制策略**：
- 本文档仅定义各库的最小可追溯字段，如更新时间、更新人等。
- 如需支持历史内容还原、知识库快照或报告与知识库版本绑定，应由专门的版本治理机制承接，本文不展开。

## 6. 关键设计原则

### 6.4 职责边界清晰

| 组件 | 职责 | 不负责 |
|------|------|--------|
| AI模型 | 识别照片中的隐患，输出隐患编码和位置 | 不生成文字描述、不判断法规依据、不提供整改建议 |
| 知识库 | 提供隐患的标准化描述、法规依据、整改建议、警示案例 | 不识别照片内容 |
| 报告生成模块 | 组装知识库匹配结果，生成结构化报告 | 不自由生成文本内容 |

### 6.2 数据标准化

- **隐患描述**：标准化、通用化，不涉及具体场景
- **法规依据**：完整引用法规名称、编号、条款编号
- **整改建议**：具体、可执行、可验收

### 6.1 可追溯性

- 报告中每个知识库匹配字段都有明确来源（见2.2输出字段映射表）
- 以"更新时间+更新人"字段记录变更信息，支持基本审计
- 历史报告内容与知识库版本的精确绑定能力不在本文展开

### 6.3 可维护性

- 知识库结构清晰，易于理解和维护
- 支持增量更新，不影响已有数据
- 提供知识库回流机制，持续优化

## 7. 数据质量保障

- 隐患描述需经专业审核，确保专业性
- 法规条款需经专业审核，确保准确性
- 整改建议需经领域审核，确保可执行性
- 定期评审知识库内容，及时更新
