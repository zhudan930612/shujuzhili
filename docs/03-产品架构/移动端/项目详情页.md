**区块说明**：

| 区块 | 内容 | 交互 |
|------|------|------|
| **待上传卡片** | ⚠️ 待上传（N张） | 红色卡片，点击进入待上传记录页，数量 = 草稿数 + 失败数 |
| **项目信息** | 名称、类型、地址、施工时间、施工单位、施工负责人、联系电话 | 电话点击可拨号 |
| **已上传** | 该项目的所有巡查图片缩略图（3列网格平铺） | 点击缩略图全屏查看 |
| **巡查记录** | 该项目的历史巡查记录时间轴 | 点击单条记录查看该批次图片 |
| **悬浮按钮** | 右下角圆形加号按钮 | 无待上传记录时点击调起相册选择器；有待上传记录时优先进入待上传记录页 |

**待上传卡片样式说明**：

| 属性 | 说明 |
|------|------|
| **位置** | 项目信息下方，已上传上方 |
| **背景色** | 浅红色背景（如 #FFF2F0），与页面白色背景区分 |
| **图标** | 左侧 ⚠️ 警告图标，红色 |
| **标题** | "待上传（N张）"，红色字体，粗体 |
| **显隐逻辑** | 有待上传数据（草稿+失败）时显示，无数据时隐藏 |
| **数量计算** | 草稿数量 + 失败数量，与项目列表页角标数字保持一致 |
| **点击交互** | 点击整行进入待上传记录页 |

**悬浮按钮样式说明**：

| 属性 | 说明 |
|------|------|
| **位置** | 页面右下角，距边缘16-20px |
| **样式** | 圆形，直径56px，主色调（如蓝色）|
| **图标** | 白色"+"号或相机图标 |
| **交互** | 点击悬浮上传按钮 |
| **动效** | 页面滚动时保持固定，可添加轻微阴影提升层级感 |
| **权限** | 如未授权相册权限，首次点击时申请授权 |

**上传入口拦截规则**：

- 项目下如不存在草稿或失败记录：点击悬浮上传按钮，直接调起相册选择器，开启新的上传会话
- 项目下如存在草稿或失败记录：点击悬浮上传按钮，先提示 `请先处理待上传图片`，不直接进入相册，优先跳转到“待上传记录页”
- 用户需先完成当前待上传会话（上传成功或手动清空），才可再次从项目详情页开启新的上传会话

**缩略图加载占位**：

| 场景 | 展示 |
|------|------|
| **加载中** | 灰色占位图 + 加载动画（转圈）|
| **加载失败** | 默认占位图，点击可重试 |


**已上传图片查看**：

**展示方式**：按项目维度聚合展示，包含该项目所有巡查记录的图片，不按巡查人或批次分组。

**适用范围**：仅适用于App 端项目详情页的“已上传图片”区域。

| 属性 | 说明 |
|------|------|
| **排序** | 按巡查时间倒序分组展示，最新巡查记录排在最前 |
| **布局** | 3列网格平铺，展示所有图片 |
| **点击交互** | App 端点击缩略图弹出全屏大图弹窗 |
| **App 端全屏预览** | 支持全屏预览和左右滑动浏览图片 |

**刷新机制**：

| 场景 | 行为 |
|------|------|
| **首次进入页面** | 自动加载已上传图片列表 |
| **从待上传记录页返回** | 自动刷新已上传图片列表（刚上传的图片需显示）|
| **从巡查记录详情返回** | 不刷新（仅查看操作无变化）|
| **上传成功后** | 待上传记录页自动返回项目详情页，详情页刷新已上传列表 |

**说明**：只要重新进入项目详情页，都必须刷新已上传图片列表，确保数据最新。

**与巡查记录的关系**：
- **已上传区域**：展示项目全部图片，用于快速浏览所有隐患照片
- **巡查记录列表**：按批次展示，用于追溯具体某次巡查的图片

**边界情况处理**：
| 场景 | 处理 |
|------|------|
| 图片数量多（>30张） | 前端分页加载或虚拟滚动，仍保持平铺展示 |
| 想查看某次特定巡查的图片 | 点击下方"巡查记录"列表，进入该批次详情页 |



**项目删除后的处理**：

当用户已进入项目详情页或待上传记录页，后台删除该项目后：

| 用户操作 | 提示 |
|----------|------|
| 点击上传/保存/任何与后台交互的操作 | Toast提示"项目已不存在，无法操作" |
| 点击返回 | 正常返回列表页，列表刷新后该项目消失 |


**上传前自动压缩策略（仅适用于App 端）**：

| 原图大小 | 处理方式 | 说明 |
|---------|---------|------|
| ≤5MB | 原图直接上传 | 保证清晰度 |
| >5MB | 自动压缩至5MB以内 | 质量压缩80%，保持分辨率，用户无感知 |

**压缩对AI训练的影响（仅适用于App 端）**：适度压缩（质量≥80%）不影响隐患识别，因为AI依赖的是边缘特征而非像素级精度。

**失败处理机制**：

| 失败原因 | 处理策略 |
|---------|---------|
| 网络异常 | 自动重试3次，仍失败则标记"待上传"存本地，用户可手动触发重新上传 |

**图片规格与并发策略**：

| 配置项 | 建议值 | 说明 |
|--------|--------|------|
| **并发上传数** | 3张 | 固定并发，平衡速度与稳定性 |
| **超时时间** | 30秒/张 | 超时时自动重试或标记失败 |


**图片格式限制**：

| 限制项 | 规则 |
|--------|------|
| **支持格式** | JPG、PNG |
| **不支持** | HEIC、GIF、视频等 |
| **尺寸要求** | 无限制 |

##### 待上传记录页

**页面用途**：统一处理两种场景的图片上传操作：
1. **相册选择后进入**：选择图片后进入此页，可预览、删除、追加后上传
2. **从项目详情页进入**：点击"待上传卡片"进入，处理已保存的草稿或失败的图片

**上传会话规则**：

- 待上传记录页承载当前项目的**未完成上传会话**
- 项目下只要存在草稿或失败记录，就不能从项目详情页直接再次进入相册开启新会话
- 用户必须先在待上传记录页完成当前会话：
  - 上传成功并清空待上传
  - 或手动删除/清空待上传记录
- 只有当前会话结束后，才允许从项目详情页再次发起新的上传会话

**继续添加规则**：

| 页面状态 | 处理方式 |
|------|---------|
| **仅有草稿** | 允许点击 `继续添加`，新选择的图片并入当前会话 |
| **出现失败记录** | 进入失败处理模式，隐藏 `继续添加`，用户先处理失败图片 |

**草稿保存机制**：

用户从相册选择图片进入待上传记录页后，**返回时弹出确认框**：

```
┌─────────────────────────────┐
│                             │
│       是否保存为草稿？       │
│                             │
│    当前有 5 张图片未上传     │
│                             │
│   ┌─────────┬─────────┐    │
│   │  不保存  │   保存   │    │
│   └─────────┴─────────┘    │
│                             │
└─────────────────────────────┘
```

| 用户选择 | 处理 |
|---------|------|
| **保存** | 图片保存为"草稿"状态，关联到该项目，下次进入待上传记录页可见 |
| **不保存** | 清除本次选择的图片，返回项目详情页，不保存任何数据 |

**两种数据状态**：

| 状态 | 说明 | 来源 |
|------|------|------|
| **草稿** | 已保存但未上传的图片 | 用户选择后点击"保存" |
| **失败** | 上传失败需重试的图片 | 上传过程中网络异常导致 |

**数据有效期与清理策略**：

| 策略 | 规则 |
|------|------|
| **有效期** | 永久保存，不自动清理 |
| **存储上限** | 不限制 |
| **存储位置** | App 本地存储（按**手机号+项目ID**隔离）|
| **手动清理** | 在「我的」页面提供「清理缓存」入口，可一键清除当前用户的所有草稿和失败记录 |

**退出登录处理**：
- 退出时不自动清理数据，仅提示用户数据会保留
- 数据与手机号绑定，同账号下次登录仍可见
- 换账号登录时数据自动隔离（不同账号互不干扰）

**多账号数据隔离说明**：

缓存数据与**登录手机号**绑定，实现多巡查员共用设备时的数据隔离：

| 场景 | 处理方式 |
|------|---------|
| **巡查员A登录** | 只显示A手机号关联的草稿和失败记录 |
| **A退出，B登录** | 自动切换为B的数据，A的数据不可见 |
| **B退出，A重新登录** | 恢复显示A的历史数据 |

**存储Key设计示例**：
```
{phone}_{projectId}_drafts   // 草稿图片
{phone}_{projectId}_failed   // 失败图片
```

**清理逻辑**：
- 退出登录时，仅询问是否清理**当前用户**的待上传数据
- 清理操作只删除当前手机号关联的数据，不影响其他用户
- 换设备登录时，由于数据存在本地，新设备看不到历史草稿

**边界情况**：
- 只有草稿：进入“仅草稿模式”，显示 `继续添加`

- 两者都没有：页面为空，显示"暂无待上传图片"
- 页面不出现“草稿和失败同时展示”的情况；一旦进入失败处理模式，页面仅保留失败图片

**上传完成后处理**：

| 结果 | 处理 |
|------|------|
| 全部成功 | Toast"上传成功"，自动返回项目详情页，待上传卡片消失；当前会话形成/补齐为1条巡查记录 |
| 部分失败 | Loading消失，列表刷新显示剩余失败图片，Toast提示"上传成功X张，X张失败"；已成功图片补入当前会话对应的原巡查记录 |
| 全部失败 | Loading消失，列表不变（全部为失败状态），Toast提示"上传失败，请检查网络" |

**Phase 2规划（方案B - 后台上传+消息推送）**：

| 阶段 | 实现方式 |
|------|---------|
| **上传交互** | 点击[重新上传]后退出页面，后台静默上传 |
| **成功通知** | 上传完成后，App 通知"项目XX上传完成" |
| **失败通知** | 上传失败后，消息推送"项目XX上传失败，点击处理" |
| **跳转处理** | 点击失败通知卡片，直接跳转到该项目的待上传页面 |

**方案对比**：
| 维度 | MVP方案A | Phase 2方案B |
|------|---------|-------------|
| 技术复杂度 | 低（页面内等待） | 高（后台任务+消息推送）|
| 用户体验 | 需等待，过程可见 | 不阻塞，事后通知 |
| 适用场景 | 图片数量较少（<20张）| 图片数量多，用户不想等待 |
| 失败处理 | 立即在页面内重试 | 通过消息卡片重新进入处理 |
