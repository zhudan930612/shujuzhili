## 设计内容
**页面用途**：统一处理两种场景的图片上传操作：
1. **相册选择后进入**：选择图片后进入此页，可预览、删除、追加后上传
2. **从项目详情页进入**：点击"待上传卡片"进入，处理已保存的草稿或失败的图片

**上传会话规则**：

- 待上传记录页承载当前项目的**未完成上传会话**
- 项目下只要存在草稿或失败记录，就不能从项目详情页直接再次进入相册开启新会话
- 用户必须先在待上传记录页完成当前会话：
  - 上传成功并清空待上传
  - 或手动删除/清空待上传记录
- 只有当前会话结束后，才允许从项目详情页再次发起新的上传会话

**继续添加规则**：

| 页面状态 | 处理方式 |
|------|---------|
| **仅有草稿** | 允许点击 `继续添加`，新选择的图片并入当前会话 |
| **出现失败记录** | 进入失败处理模式，隐藏 `继续添加`，用户先处理失败图片 |

**草稿保存机制**：

用户从相册选择图片进入待上传记录页后，**返回时弹出确认框**：

```
┌─────────────────────────────┐
│                             │
│       是否保存为草稿？       │
│                             │
│    当前有 5 张图片未上传     │
│                             │
│   ┌─────────┬─────────┐    │
│   │  不保存  │   保存   │    │
│   └─────────┴─────────┘    │
│                             │
└─────────────────────────────┘
```

| 用户选择 | 处理 |
|---------|------|
| **保存** | 图片保存为"草稿"状态，关联到该项目，下次进入待上传记录页可见 |
| **不保存** | 清除本次选择的图片，返回项目详情页，不保存任何数据 |

**两种数据状态**：

| 状态 | 说明 | 来源 |
|------|------|------|
| **草稿** | 已保存但未上传的图片 | 用户选择后点击"保存" |
| **失败** | 上传失败需重试的图片 | 上传过程中网络异常导致 |

**数据有效期与清理策略**：

| 策略 | 规则 |
|------|------|
| **有效期** | 永久保存，不自动清理 |
| **存储上限** | 不限制 |
| **存储位置** | 移动设备本地存储（按**手机号+项目ID**隔离）|
| **手动清理** | 在「我的」页面提供「清理缓存」入口，可一键清除当前用户的所有草稿和失败记录 |

**退出登录处理**：
- 退出时不自动清理数据，仅提示用户数据会保留
- 数据与手机号绑定，同账号下次在移动设备上登录仍可见
- 换账号登录时数据自动隔离（不同账号互不干扰）

**多账号数据隔离说明**：

缓存数据与**登录手机号**绑定，实现多巡查员共用设备时的数据隔离：

| 场景 | 处理方式 |
|------|---------|
| **巡查员A登录** | 只显示A手机号关联的草稿和失败记录 |
| **A退出，B登录** | 自动切换为B的数据，A的数据不可见 |
| **B退出，A重新登录** | 恢复显示A的历史数据 |

**存储Key设计示例**：
```
{phone}_{projectId}_drafts   // 草稿图片
{phone}_{projectId}_failed   // 失败图片
```

**清理逻辑**：
- 退出登录时，仅询问是否清理**当前用户**的待上传数据
- 清理操作只删除当前手机号关联的数据，不影响其他用户
- 换设备登录时，由于数据存在本地，新设备看不到历史草稿

**页面布局（失败处理模式）**：

```
┌─────────────────────────────┐
│ ← 待上传记录            清空 │
├─────────────────────────────┤
│  上传失败（1张）             │
│  ┌────┐                     │
│  │图1 │  [重新上传] [删除]   │
│  └────┘                     │
├─────────────────────────────┤
│        [      上传全部      ]│
└─────────────────────────────┘
```

**页面模式说明**：

| 模式 | 展示内容 | 说明 |
|------|---------|------|
| **仅草稿模式** | 只展示草稿图片 | 可继续添加，也可上传全部 |
| **失败处理模式** | 只展示失败图片 | 优先处理失败图片，不允许继续添加 |

**边界情况**：
- 只有草稿：进入“仅草稿模式”，显示 `继续添加`
- 只有失败：进入“失败处理模式”，隐藏 `继续添加`
- 两者都没有：页面为空，显示"暂无待上传图片"
- 页面不出现“草稿和失败同时展示”的情况；一旦进入失败处理模式，页面仅保留失败图片

**多选删除模式**：

```

│ ← 待上传记录          完成   │
```

**功能说明**：

| 功能 | 交互 | 说明 |
|------|------|------|
| 预览大图 | 点击缩略图 | App 端全屏查看，左右滑动切换 |
| 多选删除 | 长按任意缩略图 | 进入多选模式，勾选后点击底部[删除]批量移除 |
| 清除全部 | 点击右上角"清空" | 二次确认后清空当前待上传记录，返回项目详情页 |
| 继续添加 | 点击底部[+ 继续添加] | 仅在“只有草稿、没有失败”时显示；调起系统相册选择器，追加图片并归入当前会话 |
| 重新上传 | 点击失败图片行内[重新上传] | 仅重传当前失败图片；上传成功后补入当前会话对应的原巡查记录 |
| 上传全部 | 点击底部[上传全部] | 草稿直接上传；失败图片发起重传，成功后补入当前会话对应的原巡查记录 |

**上传过程**：

```
┌─────────────────────────────┐
│ ← 待上传记录                 │
├─────────────────────────────┤
│                             │
│        ┌─────────┐          │
│        │   ⏳   │          │  ← Loading动画
│        │  上传中  │          │
│        └─────────┘          │
│                             │
│   （半透明遮罩，按钮置灰）    │
│                             │
└─────────────────────────────┘
```

**上传完成后处理**：

| 结果 | 处理 |
|------|------|
| 全部成功 | Toast"上传成功"，自动返回项目详情页，待上传卡片消失；当前会话形成/补齐为1条巡查记录 |
| 部分失败 | Loading消失，列表刷新显示剩余失败图片，Toast提示"上传成功X张，X张失败"；已成功图片补入当前会话对应的原巡查记录 |
| 全部失败 | Loading消失，列表不变（全部为失败状态），Toast提示"上传失败，请检查网络" |

**Phase 2规划（方案B - 后台上传+消息推送）**：

| 阶段 | 实现方式 |
|------|---------|
| **上传交互** | 点击[重新上传]后退出页面，后台静默上传 |
| **成功通知** | 上传完成后，App 通知"项目XX上传完成" |
| **失败通知** | 上传失败后，消息推送"项目XX上传失败，点击处理" |
| **跳转处理** | 点击失败通知卡片，直接跳转到该项目的待上传页面 |

**方案对比**：
| 维度 | MVP方案A | Phase 2方案B |
|------|---------|-------------|
| 技术复杂度 | 低（页面内等待） | 高（后台任务+消息推送）|
| 用户体验 | 需等待，过程可见 | 不阻塞，事后通知 |
| 适用场景 | 图片数量较少（<20张）| 图片数量多，用户不想等待 |
| 失败处理 | 立即在页面内重试 | 通过消息卡片重新进入处理 |
