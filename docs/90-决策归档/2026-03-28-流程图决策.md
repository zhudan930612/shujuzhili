## 项目来源决策

### 项目数据来源

**决策结论**：项目数据有两个来源，备案系统同步为增值功能（能通则通），后台手动创建为保底功能（必须实现）。

**来源一：备案系统同步（增值功能）**

| 维度 | 说明 |
|------|------|
| 数据内容 | 项目全量信息（名称、类型、地址、备案编号等）|
| 同步频率 | 每日凌晨2:00自动执行 + 后台手动触发 |
| 前置条件 | 需政府部门确认数据对接可行性，可能需签署数据共享协议 |

**来源二：后台手动创建（保底功能）**

无论备案系统能否对接，后台管理系统必须支持手动创建项目：

| 场景 | 操作流程 |
|------|---------|
| 备案系统可同步 | 自动同步为主，后台可人工增补/修正 |
| 备案系统不可同步 | 运营根据保险公司服务订单或自行维护的数据，在后台手动录入 |

**后台创建项目字段**：
| 字段 | 必填 | 说明 |
|------|------|------|
| 项目名称 | 是 | 如"万科云城三期12栋" |
| 施工类型 | 是 | 家装/小型工程/零星作业（影响后续标注）|
| 项目地址 | 是 | 用于GPS校验（可选）|
| 施工时间 | 是 | 时间段，如 2026.03.01 - 2026.06.30 |
| 备案编号 | 否 | 如有则填入，用于对照 |
| 保险公司 | 是 | 关联服务订单来源 |
| 施工单位 | 否 | 施工单位名称 |
| 施工负责人姓名 | 否 | 负责人姓名 |
| 施工负责人电话 | 否 | 负责人联系电话 |

**项目创建后流向**：
```
后台创建项目 → 写入项目列表页 → 同步至小程序项目列表 → 巡查员可选择关联
```

### 备案系统同步风险与应对

**关键风险：政府侧数据外流限制**

| 风险项 | 说明 | 影响 |
|--------|------|------|
| 备案系统部署在政府侧服务器 | 备案数据含用户敏感信息，政府可能不允许数据同步到互联网平台 | 无法自动同步项目列表，小程序无法扫码/选择项目关联 |

**风险应对预案**：

| 情况 | 应对方案 |
|------|---------|
| 允许数据同步 | 按原计划执行，每日同步备案项目数据 |
| 不允许同步，但允许脱敏查询 | 小程序扫码/搜索时实时查询政府侧接口，不落库 |
| **完全不允许对接** | **改用保险公司指派项目预录入** |

**保险公司预录入方案（备案系统不可对接时的替代）**：

| 环节 | 说明 |
|------|------|
| 数据来源 | 保险公司事故预防服务订单（含项目地址、类型、施工内容）|
| 录入方式 | 运营人员在后台预录入，创建项目基本信息 |
| 同步时机 | 巡查员出发前，项目已存在于平台，小程序可选择 |

**方案对比**：
| 维度 | 备案系统同步 | 保险公司预录入 |
|------|-------------|----------------|
| 数据获取难度 | 需政府审批，难度高 | 保险公司合作方，易获取 |
| 数据完整性 | 完整（含备案全量信息）| 依赖保险公司提供字段 |
| 运营工作量 | 低（自动同步）| 高（需人工录入）|
| 合规风险 | 有（政务数据外流）| 低（商业合作数据）|
| 巡查员体验 | 扫码/选择项目 | 相同 |
| 标注质量 | 高（施工类型准确）| 高（保险公司提供类型）|

### 项目列表推送至小程序

**决策结论**：项目数据直接写入后台管理系统项目列表页并推送至小程序，不做筛选或确认。

**决策理由**：
- **备案侧全权管理**：项目数据的质量、有效性完全由备案系统负责，数据治理平台不做干预
- **被动接收原则**：平台只消费备案系统推送的数据，不做"脏数据"判断或过滤
- **减少中间环节**：去掉运营确认环节，避免人为延迟，巡查员可即时看到最新项目

**数据流转**：
```
备案系统/后台创建 → 自动同步 → 后台管理系统项目列表页 + 推送小程序
                              ↓
                        失败告警 → 人工介入（技术层面，非数据审核）
```

**异常处理**：
- 同步失败（网络/接口问题）：技术告警，人工修复同步机制
- 数据内容问题（项目错误/重复）：反馈给备案侧处理，平台不做本地修正

## 采集端设计决策

### 移动端上传方式优先级决策

**决策结论**：MVP阶段优先实现"方式2（原相机拍照 + 小程序批量上传）"，"方式1（小程序现场拍照）"后置到Phase 2。

**决策理由**：
- **技术复杂度对比**：方式1涉及断网存储、上传续传、连拍管理、本地缓存清理等复杂逻辑；方式2只需调用 wx.chooseMedia 选择相册图片，技术简单
- **页面数量对比**：方式1需要拍照页、待确认页、离线管理页等；方式2只需项目详情页 + 相册选择器
- **边界情况**：方式1需处理网络中断、存储空间不足、后台上传、权限被拒等多种异常；方式2异常场景少
- **用户习惯匹配**：巡查员已习惯原相机拍照，方式2不改变拍摄习惯，只优化上传环节

**三种方式定位**：
| 方式 | 描述 | MVP阶段 | 占比预测 | 理由 |
|------|------|---------|---------|------|
| **方式2：原相机+小程序批量上传** | 相机拍照 → 小程序选相册 → 批量上传 | **必须实现** | 70% | 技术简单，最符合巡查员 workflow |
| **方式3：后台批量导入** | 相机拍照 → 事后电脑登录后台 → 选项目 → 上传 | **保留可用** | 25% | 兜底方式，老巡查员过渡用 |
| **方式1：小程序现场拍照** | 小程序内连拍 → 待确认 → 上传 | **后置到Phase 2** | 5% | 技术复杂，MVP阶段投入产出比低 |

**方式2详细流程**：
```
项目详情页 → 点击右下角悬浮"+"按钮 → 微信相册选择器（wx.chooseMedia）→ 选择多张 → 自动上传 → 上传成功
```

**方式3：后台批量导入（兜底方式）**

**决策结论**：保留后台批量导入功能，作为巡查员不使用小程序时的兜底方案。

**决策理由**：
- **过渡需求**：部分老巡查员习惯用电脑整理，强制切换小程序会导致抵触
- **技术简单**：后台上传组件成熟，开发成本低
- **应急备用**：小程序故障或巡查员手机没电时，有替代方案

**流程设计**：
```
相机拍照 → 事后开电脑 → 登录后台管理系统 → 选择项目 → 批量上传图片 → 关联成功
```

**功能清单**：
| 功能 | 说明 |
|------|------|
| 项目选择 | 下拉选择或搜索项目 |
| 批量选择 | 支持 Ctrl/Shift 多选图片 |
| 上传进度 | 显示上传进度条 |
| 失败重试 | 失败任务可重新上传 |

**使用占比预测**：25%，主要面向习惯电脑操作的老巡查员和应急场景。

**方式1：小程序现场拍照（Phase 2 规划）**

**决策结论**：方式1（小程序现场连拍）后置到Phase 2，MVP阶段仅做预留接口。

**决策理由**：技术复杂度高（断网存储、上传续传、本地缓存管理），MVP阶段优先实现更简单的方式2。

**Phase 2 功能概要**：
- 项目详情页进入现场拍照模式
- CameraContext 连拍，拍完后进入待确认页
- 支持删除、全屏查看、批量选择
- 离线存储，有网后自动/手动上传
- 可选保存到本地相册（双写）

详细设计待Phase 2启动时再细化。

### 小程序功能极简（零标注）

**决策结论**：小程序只做三件事：进入项目、选择图片、批量上传。不做任何现场标注或信息填写。

**决策理由**：
- **配合度优先**：巡查员是"我们自己的人"，但配合度需要维护；每多一个步骤，流失率上升
- **核心路径≤3步**：进入项目→拍照→完成，现场操作越快越好
- **信息后置**：隐患类型、法规关联等专业判断，交给后端标注员更专业；巡查员现场判断容易错，反而污染数据

**舍弃的功能及原因**：
| 功能 | 舍弃原因 | 替代方案 |
|------|---------|---------|
| 现场隐患标注 | 增加负担，降低配合度 | 后置到S4标注环节 |
| 语音描述 | Phase 1暂不需要，保持极简 | Phase 2生成报告时考虑 |
| 实时质量检测 | 不是数据治理平台职责 | 巡查团队自行把控 |

### 照片必须与项目关联

**决策结论**：所有照片必须关联到具体项目，但关联方式灵活（扫码/列表选择/事后补录）。

**决策理由**：
- **标注质量依赖**：施工类型（家装/小型工程/零星作业）是隐患类型预测、法规关联的强特征
  - 例："电线裸露"在家装和工地的法规条款完全不同
  - 不关联项目，标注员无法判断场景，法规关联错误率飙升
- **备案系统已有数据**：既然是我们自建的备案系统，项目数据唾手可得，不利用是浪费

**关联方式设计**：
| 方式 | 优先级 | 使用场景 |
|------|--------|---------|
| 扫现场二维码 | 推荐 | 现场有码且清晰，最快捷 |
| 项目列表选择 | 备选 | 无二维码或网络差 |
| 事后补录 | 兜底 | 特殊情况，24小时内运营补关联 |

**技术实现**：
- 一次进入项目，批量上传自动继承项目ID
- S4标注员可见施工类型信息（水印方案详见「图片水印方案」节，待确认）

##### 登录页

**决策结论**：登录页面主要以手机验证码登录为主，同时提供微信小程序一键登录按钮。

**用户权限规则**：
- 允许登录的账户必须在后台管理系统中已创建
- 未在后台创建的手机号，即使验证码正确也提示"无权限查看"或类似提示
- 后台管理员可提前导入巡查员手机号，或运营手动创建账号

│                             │
│                             │
│  ┌─────────────────────┐   │

**功能说明**：

| 元素 | 交互 | 说明 |
|------|------|------|

| 微信一键登录 | 调起微信授权 | 获取微信手机号，同样校验是否在白名单中，首次登录也需确认协议 |

**协议相关说明**：
- 首次登录必须勾选同意协议，勾选状态本地存储
- 协议内容更新时，下次登录需重新确认
- 未勾选协议时点击登录，提示"请先阅读并同意用户协议"

**无权限提示**：
- 当手机号验证码正确但未在后台创建时，提示："您暂无巡查权限，请联系管理员添加账号"
- 引导用户联系平台运营人员

**时间轴设计说明**：

| 元素 | 说明 |
|------|------|
| **● 日期节点** | 实心圆点标记日期，同一天的多条记录共享一个日期节点 |
| **│ 时间线** | 竖线连接同一天内的多次巡查记录 |

**时间轴样式规则**：

| 场景 | 展示方式 |
|------|---------|
| **不同日期** | 新的●日期节点，与前一条记录有明显间距 |
| **同一天多次** | 共享日期，用│连接，下方以○标记具体时间 |
| **最新记录** | 最上方，●节点可高亮（如蓝色或加粗）|
| **历史记录** | 正常显示，按时间倒序排列 |

**排序规则**：按巡查时间**倒序排列**（最新的巡查记录在最上面）。

**巡查记录判定规则**：

巡查记录以**完整上传会话**为粒度进行区分，具体规则如下：

| 规则项 | 说明 |
|--------|------|
| **会话开始时机** | 用户从项目详情页发起一次新的上传操作，且当前项目下不存在草稿或失败记录 |
| **记录创建条件** | 当前上传会话内至少1张图片成功上传，即生成一条巡查记录 |
| **同一项目多次巡查** | 同一项目可有多次独立巡查；仅当前一上传会话已完成或被清空后，下一次上传才生成新记录 |
| **失败重传处理** | 同一会话内如部分图片上传失败，失败图片后续重传成功时补入原巡查记录，不生成新记录 |
| **草稿处理** | 草稿仅表示未完成会话，不生成巡查记录；草稿后续上传成功时归入当前会话对应的巡查记录 |

**场景示例**：
- 场景1：巡查员A对项目X进行巡查，一次性上传15张图片全部成功 → 生成1条巡查记录（15张）
- 场景2：巡查员A对项目X巡查，选择20张图片上传，因网络问题仅10张成功 → 先生成1条巡查记录；剩余10张稍后在待上传页重传成功 → 补入原巡查记录，不新增记录
- 场景3：巡查员A周一巡查项目X上传8张，周三再次巡查同一项目上传12张 → 生成2条独立巡查记录

**设计理由**：
- 保持“一次巡查 = 一次完整上传会话”的用户心智，避免同一次巡查被拆成多条记录
- 网络不稳定场景下，成功数据可先入库，失败图片后续补齐，不影响巡查次数统计
- 草稿、失败、重传都围绕同一未完成会话处理，业务边界更清晰

**页面用途**：统一处理两种场景的图片上传操作：

**上传会话规则**：

- 待上传记录页承载当前项目的**未完成上传会话**
- 项目下只要存在草稿或失败记录，就不能从项目详情页直接再次进入相册开启新会话
- 用户必须先在待上传记录页完成当前会话：

- 退出时不自动清理数据，仅提示用户数据会保留

- 换账号登录时数据自动隔离（不同账号互不干扰）

**多账号数据隔离说明**：

缓存数据与**登录手机号**绑定，实现多巡查员共用设备时的数据隔离：

| 场景 | 处理方式 |
|------|---------|
| **巡查员A登录** | 只显示A手机号关联的草稿和失败记录 |
| **A退出，B登录** | 自动切换为B的数据，A的数据不可见 |
| **B退出，A重新登录** | 恢复显示A的历史数据 |

| **上传交互** | 点击[重新上传]后退出页面，后台静默上传 |
| **成功通知** | 上传完成后，小程序服务通知"项目XX上传完成" |
| **失败通知** | 上传失败后，消息推送"项目XX上传失败，点击处理" |
| **跳转处理** | 点击失败通知卡片，直接跳转到该项目的待上传页面 |

**方案对比**：
| 维度 | MVP方案A | Phase 2方案B |
|------|---------|-------------|
| 技术复杂度 | 低（页面内等待） | 高（后台任务+消息推送）|
| 用户体验 | 需等待，过程可见 | 不阻塞，事后通知 |
| 适用场景 | 图片数量较少（<20张）| 图片数量多，用户不想等待 |
| 失败处理 | 立即在页面内重试 | 通过消息卡片重新进入处理 |

### 图片水印方案（待确认）

**当前状态**：等待确认保险公司对水印的具体要求，两种技术方案待决策。

**方案A：强制小程序现场拍照（原方案）**

| 环节 | 说明 |
|------|------|
| **适用条件** | 保险公司要求可见水印，且必须体现在原始图片上 |
| **采集方式** | 强制使用方式1（小程序现场拍照） |
| **技术实现** | 小程序拍照时不叠加水印，原始图片上传平台；展示/导出时前端叠加 |
| **优缺点** | ✅ 训练数据绝对纯净；❌ 必须推广小程序拍照，开发复杂度高，巡查员需改变习惯 |

**方案B：统一原始图片上传，导出时叠加水印（优化方案）**

| 环节 | 说明 |
|------|------|
| **适用条件** | 保险公司要求可见水印，但接受导出时添加 |
| **采集方式** | 三种方式均可（小程序拍照/原相机+移动端上传/后台导入） |
| **技术实现** | 任意方式上传原始图片；后台管理系统导出整改报告时前端叠加水印 |
| **优缺点** | ✅ 训练数据纯净；✅ 不限制巡查员使用习惯；✅ 开发成本相对较低 |

**方案C：仅EXIF元数据（无可见水印）**

| 环节 | 说明 |
|------|------|
| **适用条件** | 保险公司接受EXIF元数据作为溯源依据，不要求可见水印 |
| **采集方式** | 三种方式均可 |
| **技术实现** | 原相机EXIF含时间/GPS，平台补充项目ID；无需叠加可见水印 |
| **优缺点** | ✅ 方式最灵活；✅ 无额外开发成本；✅ 巡查员零负担 |

**待确认事项**：
| 问题 | 影响 | 跟进时机 |
|------|------|---------|
| 保险公司是否要求**可见水印** | 如要求，需在方案A和方案B中选择；如不要求，采用方案C | 与保险公司合作洽谈时确认，优先级**高** |
| 如要求可见水印，是否接受**导出时添加** | 决定采用方案A（强制小程序）还是方案B（方式灵活） | 与保险公司合作洽谈时确认 |

## 巡查管理模块

**模块定位**：统一管理后台和小程序产生的巡查记录，以“上传会话”为最小管理单元，支持全局检索、上传、查看、编辑和图片清理。

**核心口径**

- 巡查记录归属口径沿用前文“巡查记录判定规则”，后台与小程序统一按完整上传会话处理
- 移动端上传和后台上传都会生成巡查记录，且都必须关联项目
- 后台上传可手动指定 `巡查人`，默认当前后台操作人；`上传人` 固定记录为当前后台操作人
- `巡查时间` 为主显示时间，`上传时间` 为辅助时间
- 巡查记录不设置独立 `状态` 字段
- 图片不支持追加到原记录，也不支持替换原图片；仅支持在详情页对当前记录图片进行批量删除
- 巡查记录仅支持在详情页单条删除；删除某项目最后一条巡查记录后，项目状态自动恢复为 `未巡查`

**保存规则**

**1. 记录生成规则**

- 点击 `保存` 时，前置条件为至少有 `1` 张上传成功图片；满足条件后先弹出保存确认弹窗
- 保存确认弹窗展示 `项目名称 / 项目地址 / 巡查时间 / 巡查人 / 图片数量`，并明确提示保存后仅支持删除图片，不支持追加图片
- 用户在确认弹窗中点击 `确定` 后，生成 `1` 条新的巡查记录
- 不支持向已有巡查记录追加图片；保存成功后，该巡查记录仅支持删除图片，不支持再追加图片

**2. 上传区展示与操作**

- 已选图片支持在保存前逐张删除；删除后即时更新展示区内容；当删除至 `0` 张时恢复为空状态
- 上传区不展示图片级失败状态，不提供失败列表、重新上传、删除失败图或全部清除失败图的交互

**3. 保存结果与异常处理**

- 点击 `保存` 时如无成功图片：不生成巡查记录，并提示 `请至少上传1张图片`
- 点击 `保存` 后弹出确认弹窗，提示 `保存后只能删除图片，无法追加图片操作，确认是否保存？`
- 保存成功后：返回巡查记录列表，并提示“保存成功”

**详情规则**

**图片管理规则**

- 仅支持对当前巡查记录下的图片执行删除管理
- 点击图片列表区右侧 **[批量管理]** 后，页面进入批量管理态
- 批量管理态下，每张图片右上角显示 **[删除]** 操作，点击后将该图片标记为待删除
- 批量管理态下，图片区标题右侧显示 **[取消]**、**[保存]**
- 点击 **[取消]**：放弃本次图片删除操作，返回详情态
- 点击 **[保存]**：如当前存在已标记删除的图片，先校验删除后图片数量是否大于等于 `1`；若删除后数量为 `0`，则阻断保存并在页面顶部以 Toast 提示“巡查记录至少保留 1 张图片，如需清空请使用「删除记录」”；校验通过后弹出确认弹窗，提示“删除图片后无法恢复，且该巡查记录不支持追加图片，请谨慎操作。是否确认保存？”；用户确认后统一提交本次删除结果，删除成功后返回详情态，并同步刷新图片数量
- 不支持对已有巡查记录追加图片
- 不支持替换已有图片

**删除记录规则**

- 详情态底部按钮区包含 **[删除记录]**，点击后弹出二次确认弹窗，提示“确认删除将同时删除当前巡查记录及关联的所有图片，删除后无法恢复。是否确认删除？”
- 用户确认后删除该巡查记录及其关联的全部图片，删除成功后返回巡查记录列表页
- 删除某项目最后一条巡查记录后，该项目状态自动回写为 `未巡查`

**决策原因**

- 巡查记录已定义为“一次完整上传会话形成的结果”，记录生成后应保持边界稳定，避免后续追加图片改变原记录语义
- 允许删除图片是为纠错，不改变“这是哪一次巡查”的归属；允许追加图片则会模糊巡查时间、上传时间、图片数量和巡查次数的统计口径
- 记录生成前，用户仍可在上传会话中继续添加或删除图片；记录生成后仅保留删图能力，便于纠错且不破坏审计与追溯

**模式规则**

- 同一子页面承载四种模式：`新增`、`详情`、`编辑`、`复制`
- 页面主体字段结构一致，模式差异仅体现在标题、字段是否可编辑、底部按钮、是否显示前后切换
- 新增模式：空表单，`隐患编码` 不展示，底部按钮为 `[取消] [保存]`
- 详情模式：字段只读，底部按钮为 `[上一条] [下一条] [编辑] [复制] [停用/启用]`
- 编辑模式：预填当前隐患数据，`隐患编码`、`行业域`、`一级分类`、`二级分类` 只读，底部按钮为 `[取消] [保存]`
- 复制模式：预填当前隐患数据但不带原 `隐患编码`；除隐患编码外，其余业务字段均可调整，底部按钮为 `[取消] [保存]`

**编辑与复制规则**

- 点击列表行内 `编辑` 后，进入子页面编辑模式并预填当前隐患信息
- 点击列表行内 `复制` 或详情模式底部 `复制` 后，进入子页面复制模式；除 `隐患编码` 外，其余字段全部按当前隐患预填，`行业域`、`一级分类`、`二级分类`、`隐患名称`、`隐患描述`、`隐患等级`、`整改措施`、`整改期限`、`备注`、`关联法规` 均允许修改
- 复制保存时，系统根据最新填写的结构字段与业务内容重新生成新隐患编码，不覆盖原隐患记录
- 新增或复制保存成功后，Toast 中显示新生成的隐患编码，并进入该隐患的详情模式
- 编辑保存成功后，留在当前隐患的详情模式并刷新页面内容

**详情模式连续浏览**

- `上一条 / 下一条` 仅保留在详情模式
- 点击 `上一条 / 下一条` 不离开当前子页面，直接在详情模式内切换内容
- 切换顺序严格按照用户进入详情时的列表顺序执行，继承当时的搜索条件、筛选条件、排序规则和分页结果
- 打开详情模式时，系统需记录当前记录在列表结果集中的位置，用于前后切换
- 当前为第一条时，`上一条` 置灰不可点；当前为最后一条时，`下一条` 置灰不可点
- 从详情切到编辑后，保存返回当前记录详情；从详情切到复制后，保存进入新记录详情

| 字段 | 必填 | 说明 |

| 隐患名称 | 是 | 四级具体隐患名称，如“防护栏杆高度不足” |
| 隐患描述 | 是 | 标准化描述，用于报告输出 |
| 隐患等级 | 是 | 单选：重大/较大/一般 |

**关联法规选择交互**

1. 点击 **[+ 关联]** → 打开“关联法规选择弹窗”

**关联类型说明**
- **主要依据**：条款直接明确规定该隐患的具体技术要求
- **参考依据**：条款从更宏观角度涉及该隐患，但不是直接技术规定

**编码生成规则**

**编码结构**

格式：`[行业域代码]-[事故类型代码]-[检查点位代码]-[四级序号]`

| 层级 | 说明 | 示例 |
|------|------|------|
| 行业域代码 | 一级结构，统一采用两字母代码 | JZ（建筑施工）、WH（危险化学品） |
| 事故类型代码 | 二级结构，按行业域内事故类型定义英文代码 | FALL、STRIKE、ELEC |
| 检查点位代码 | 三级结构，按行业域 + 事故类型下的检查点位定义英文代码 | EDGE、SCAFFOLD、ELECBOX |
| 四级序号 | 四位数字，自增维护 | 0001、0002、0003 |

**生成逻辑**

1. 用户选择行业域、一级分类（事故类型）和二级分类（检查点位）后，系统自动确定编码前缀
2. 系统按行业域维度维护该结构下的当前最大序号，加1生成新的四级序号
3. 拼接生成完整编码，用户不可修改

**约束规则**

| 规则 | 说明 |
|------|------|
| 唯一性 | 编码全局唯一，已使用的编码永不回收 |
| 不可编辑 | 隐患创建后编码不可修改 |
| 结构归属 | 行业域、事故类型、检查点位与编码前缀强绑定 |
| 批量导入 | 系统忽略Excel中的编码列，根据结构字段自动生成 |

| 隐患三级类型字典 | 所属行业域、所属隐患二级类型、类型编码、类型名称 | 对应检查点位，如 `EDGE / 临边洞口` |

- 点击行内 `[编辑]`，打开编辑弹窗并预填当前数据

- 点击行内 `[详情]`，查看当前字典项完整信息

**搜索与筛选**

- 搜索支持：编码、名称模糊搜索
- 状态筛选：全部 / 启用 / 停用
- 层级型字典额外支持按上级字典筛选

#### 新增/编辑字典项弹窗

**触发方式**：点击字典列表右上角 `[+ 新增字典项]` 或行内 `[编辑]`

**弹窗规则**

- 弹窗标题根据当前字典类型动态变化，如“新增项目编码类型”“新增行业域”“编辑法规类型”“新增隐患二级类型”
- 新增模式允许填写全部字段；编辑模式保留已创建字典项的当前值并允许修改
- 隐患二级类型字典在编辑模式下，`所属行业域` 为只读，不允许修改
- 隐患三级类型字典在编辑模式下，`所属行业域`、`所属隐患二级类型` 为只读，不允许修改
- 层级型字典弹窗需先选择上级字典，再填写编码和名称
- `状态` 默认 `启用`

**决策原因**

- 二级类型和三级类型都属于层级结构节点，修改上级归属不是普通编辑，而是将该节点迁移到另一棵分类树下
- 如放开修改 `所属行业域` 或 `所属隐患二级类型`，会直接影响已引用这些字典项的隐患数据归属，容易造成分类结构漂移
- 因此新增时允许选择上级归属，编辑时仅允许修改当前节点自身信息，如 `编码 / 名称 / 状态 / 备注`

**弹窗字段**

| 字典类型 | 字段 |
|---------|------|
| 项目编码类型字典 | 施工类型名称、编码前缀、状态、备注 |
| 行业域字典 | 编码、名称、状态、备注 |
| 法规类型字典 | 编码、名称、状态、备注 |
| 隐患二级类型字典 | 所属行业域、编码、名称、状态、备注 |
| 隐患三级类型字典 | 所属行业域、所属隐患二级类型、编码、名称、状态、备注 |

**唯一性校验**

- 行业域字典：行业域编码全局唯一，行业域名称全局唯一
- 项目编码类型字典：施工类型名称全局唯一，编码前缀全局唯一
- 法规类型字典：法规类型编码全局唯一，法规类型名称全局唯一
- 隐患二级类型字典：类型编码全局唯一；类型名称在同一行业域下唯一
- 隐患三级类型字典：类型编码全局唯一；类型名称在同一行业域和同一隐患二级类型下唯一

#### 字典详情弹窗

**触发方式**：点击行内 `[详情]`

**弹窗规则**

- 弹窗标题根据当前字典类型动态变化，如“项目编码类型详情”“行业域详情”“法规类型详情”“隐患三级类型详情”
- 弹窗内容全部只读展示，不支持在弹窗内直接编辑
- 层级型字典需展示完整上级关系，如“所属行业域”“所属隐患二级类型”
- 弹窗底部仅保留 `[关闭]`

**状态与删除规则**

- 字典项默认支持 `启用 / 停用`
- 未被业务数据引用的字典项允许删除
- 已被项目管理、隐患库、法规库引用的字典项不允许物理删除，只允许停用
- 停用后不再出现在新增/编辑表单下拉中，但历史数据仍按原值正常展示
- 项目编码类型字典直接影响项目编号前缀；停用后不影响已生成项目编号展示，但默认不建议停用预置三项

**与业务模块联动**

- 项目编码类型字典：影响项目管理中的项目编号生成前缀，手动创建和批量导入均按该字典映射生成项目编号
- 行业域字典：影响隐患库、法规库中的适用行业/行业域下拉与编码前缀
- 法规类型字典：影响法规库新增、编辑、导入的法规类型下拉
- 隐患二级类型字典：影响隐患库中的事故类型下拉
- 隐患三级类型字典：影响隐患库中的检查点位下拉
- 拖动排序变化后，前台页面和后台表单中的下拉顺序同步更新
