# 任务执行协议

## 文档定位
- 本文件定义 AI 或人工处理常见产品设计任务时“怎么完成一类任务”。
- 本文件不承载业务主定义，不替代正式 PRD、产品架构、业务流程或归档决策。
- 任务执行时应先找到主定义，再判断影响范围，最后同步受影响资产。

## Harness 定义
- 本仓库 Harness = `AGENTS.md` + 目录 README + 任务执行协议 + 任务完成检查 + 工具脚本 + 人工确认点。
- `AGENTS.md`：顶层规则和目录地图。
- 目录 README：局部规则和资产归位。
- 任务执行协议：任务开始前的流程引导。
- 任务完成检查：任务结束前的收尾检查。
- [../06-工具脚本/run_checks.py](../06-工具脚本/run_checks.py)：统一机械检查入口。
- 人工确认点：业务取舍、产品范围、权限规则、法规匹配、页面交互。

## 默认执行入口
- 产品设计、PRD、原型、模板、需求沟通类任务，默认先走本协议，再走 [任务完成检查.md](任务完成检查.md) 收尾。
- 执行协议不以“口头说已遵循”为准，而以是否留下协议要求的过程产物、拆回痕迹和收尾说明为准。
- `python 06-工具脚本/run_checks.py --scope all` 只检查结构性闭环，不判断业务结论对错；脚本通过不等于评审充分或方案正确。
- 同类错误一旦出现，默认进入 [错误治理清单.md](错误治理清单.md) 判断要升级为 `Guide / Golden Path / Sensor / Ratchet` 的哪一层。

## 编辑前避错检查
- 凡是修改 `02-PRD文档/后台管理/*.md`，尤其进入“通用规则 / 跨页面共用规则”或“页面需求”章节前，必须先按 [错误治理清单.md](错误治理清单.md) 做一次编辑前避错检查，再落笔修改。
- 已登记错误不只用于事后登记或收尾复盘；命中同类场景时，必须先参考清单里的“编辑前必查信号”和“默认处理动作”做自检。
- 页面级 PRD 收口前，至少完成以下四项判断：
  - `规则归属判断`：本次新增或调整的规则，属于模块唯一口径，还是页面触发规则。
  - `页面有效内容判断`：本次保留的内容，是否为本页实际展示、实际操作、实际状态或实际异常所必需，而不是横向对比带出来的历史残留说明。
  - `表达方式判断`：是否出现“至少”“等”“包括但不限于”“无按钮/无入口/无展示”这类高风险表达。
  - `对象闭合判断`：同一对象是否在页面状态、字段展示、操作规则、弹窗结果之间出现互斥描述。
- 对“模块通用规则 / 跨页面共用规则”执行硬判断：凡是依赖具体页面入口、按钮、弹窗、抽屉、列表项点击、页面展示区或页面操作阻断条件才能成立的规则，默认不进入模块通用规则，优先下沉到对应页面章节；只有跨多个页面复用且必须唯一主定义的规则，才允许留在模块级。

## 通用执行顺序
| 步骤 | 动作 | 输出 |
|------|------|------|
| 1 | 理解输入 | 明确用户诉求、来源资料、约束和待解决问题 |
| 2 | 查找主定义 | 找到业务规则、页面规则、字段规则或流程规则所在主文档 |
| 3 | 评审合理性 | 指出完整性、边界条件、潜在问题和可替代方案 |
| 4 | 更新目标文档 | 只在主定义或当前阶段应承载的文档中修改 |
| 5 | 同步受影响资产 | 检查 PRD、原型、模板、流程图、归档记录之间的影响 |
| 6 | 完成检查 | 按 [任务完成检查.md](任务完成检查.md) 做收尾验证 |

## 中间产物保留规则
- 复杂文档任务应保留关键中间判断，而不是只保留最终 PRD。
- 应保留的中间判断包括：需求背景、约束、方案取舍、评审意见、修订原因、待确认问题。
- 中间判断优先进入“基于 [需求沟通模板.md](需求沟通模板.md) 新建的需求沟通文档”或 [评审记录.md](评审记录.md)。
- 稳定规则必须拆回正式 PRD、产品架构、业务流程或归档记录。
- 过程文档只保留判断依据、取舍摘要和链接，不长期承载完整主定义。
- 页面草图只服务于需求沟通和结构收敛；需求沟通文档在 `草图 / 对应原型` 章节维护 ASCII 草图。拆回正式 PRD 时，在同一位置将草图替换为 `对应原型` 链接，正式 PRD 不长期维护草图正文。

## 错误升级协议
- 当用户指出“这个错不应再犯”或同类错误重复出现时，不只修当前结果，还必须补一项制度化动作。
- 制度化动作按以下顺序择一或组合推进：
  1. `Guide`：补到对应 README、协议、规则文档。
  2. `Golden Path`：补模板、骨架、组件映射模板、默认起手路径。
  3. `Sensor`：补脚本检查和测试。
  4. `Ratchet`：补收尾强制问题或评审关口。
- 若本轮无法立即实现脚本或模板，也必须先登记到 [错误治理清单.md](错误治理清单.md)，避免错误再次只停留在对话里。

## 需求沟通落地闭环
- 需求沟通中出现明确结论、待确认问题、方案取舍、用户否定项时，必须写入文档，不只停留在对话中。
- 过程讨论优先写入“基于 [需求沟通模板.md](需求沟通模板.md) 新建的需求沟通文档”；评审性复盘优先写入 [评审记录.md](评审记录.md)。
- 稳定规则必须拆回正式 PRD、产品架构、业务流程或归档记录。
- 每个复杂需求专题必须维护“拆回正式文档清单”，记录结论、主定义文档、影响资产、状态和备注。
- 未拆回前，过程文档可承载阶段性结论；拆回后，过程文档只保留摘要、原因和链接。
- 落地状态统一使用：`待确认`、`沟通中`、`已确认`、`待拆回`、`已拆回`、`待归档`、`已归档`、`已拒绝`。
- 角色到页面/操作/数据范围权限的主定义统一以 [../02-PRD文档/后台管理/系统管理.md](../02-PRD文档/后台管理/系统管理.md) 为准。
- 页面 PRD、过程文档和评审记录只保留权限相关行为，不重复完整维护角色权限矩阵或页面权限矩阵。
- 历史过程文档可暂时保留旧写法；从新增页面需求和后续新专题开始，统一按本协议收敛权限写法。

## 需求沟通输出框架
- [需求沟通模板.md](需求沟通模板.md) 是后续需求沟通的默认骨架模板；无特殊说明时，应先基于该模板新建需求沟通文档，再按该文档结构输出需求分析、模块拆分、页面规则、弹窗规则和待确认问题。
- 模板文件本身不直接承载某一轮具体需求内容，只维护结构、占位和通用写法。
- 新建需求沟通文档默认命名为 `YYYY-MM-DD-需求主题-需求沟通.md`；如需其他命名，必须保证能从文件名直接识别专题。
- 新建需求沟通文档时，只保留模板正文骨架；模板标题、模板说明和使用说明不进入实例文档。
- 复杂功能需求不得只按用户追问逐项记录；应先输出一版完整需求草案，再围绕缺口逐项确认。
- 每次新需求沟通必须按“功能与场景分析 -> 按模块组织需求 -> 模块定位与边界 -> 模块通用规则 -> 模块页面目录 -> 模块页面需求 -> 模块状态与待确认 -> 拆回正式文档清单”的固定工作流推进。
- 用户只给出“大概要实现哪些功能”时，AI 不应直接追问字段细节；必须先自行分析核心功能、业务对象、典型场景、影响范围、跨模块边界和可能页面，再把不确定项列为待确认问题。
- 页面和弹窗/抽屉由 AI 先按模块给出拆分建议；每个模块内部参考正式 PRD 模块结构组织：模块定位、模块边界、通用规则、页面目录、页面需求、跨页面状态与数据流、待确认问题。用户确认模块内页面目录后，先检查该模块是否存在跨页面共用的业务对象、状态、字段、编码、校验、追溯规则；权限相关行为放在具体页面章节中，不放在模块通用规则里。
- 每次讨论新页面需求时，必须先制定沟通结构、页面目标和核心操作，再进入字段、状态、异常和草图细节；沟通阶段只维护 ASCII 草图，不要求原型图链接。
- 新页面需求沟通开始时，应先在对话中输出 `Qx-y-1：页面目标和核心操作`，包含目标表、核心操作建议和待确认问题；用户确认后，再写入过程文档或进入下一组问题。
- 每个页面或功能的过程性需求描述，应优先按以下骨架组织：

### 需求沟通固定工作流
| 阶段 | AI 必做动作 | 过程产物 | 进入下一阶段条件 |
|---|---|---|---|
| 1. 功能与场景分析 | 基于用户原始描述分析功能、场景、业务对象、使用对象、系统能力和成功状态；不合理或被否定的需求不沉淀为待实现内容 | 新建需求沟通文档中的“功能与场景分析” | 功能和场景已能映射到业务对象或待确认问题 |
| 2. 按模块组织需求 | 在需要承接的模块下自行拆分模块；模块不明确时先用 `模块 1`、`模块 2` 占位，沟通后改成真实模块名称 | 各 `模块 N` 章节 | 模块数量和模块占位基本清楚 |
| 3. 模块定位与边界 | 每个模块按正式 PRD 结构补充模块定位、模块边界、包含/不包含、上下游影响 | 各模块下的“模块定位”“模块边界” | 模块目标、边界和不做范围基本清楚 |
| 4. 模块通用规则 | 在每个模块下沉淀跨页面共用的业务对象、状态、字段、编码、校验、追溯规则；权限相关行为放在具体页面章节 | 各模块下的“通用规则 / 跨页面共用规则” | 模块级共用规则已确认、暂缓或标记待确认 |
| 5. 模块页面目录 | 在每个模块下拆分页面、弹窗/抽屉、主要入口和页面关系 | 各模块下的“页面目录索引” | 用户确认各模块页面目录，或待确认问题已列出 |
| 6. 模块页面需求 | 按模块、页面逐个输出目标、入口、结构、字段、操作、状态、校验、异常、衔接和追溯 | 各模块下的“页面需求”章节 | 页面关键规则已标明状态 |
| 7. 模块状态与待确认 | 每个模块维护跨页面状态与数据流、模块待确认问题；跨模块问题进入全局待确认或跨模块状态流 | 各模块下的“跨页面状态与数据流”“待确认问题清单” | 问题已逐项确认、暂缓或待研发确认 |
| 8. 拆回与收尾 | 将稳定规则拆回正式 PRD、原型、流程图、模板或归档记录 | “拆回正式文档清单”和收尾说明 | 主定义已更新或明确待拆回原因 |

- 上述阶段不能跳过；确需跳过时，必须在对话或过程文档中说明原因。
- 对话中可以先输出阶段性判断；用户明确“更新文档”“按建议”“按计划实施”后，应把已确认内容写入基于模板新建的需求沟通文档或正式主定义文档。
- 固定工作流是沟通顺序，不代表所有需求都要生成完整 PRD；小需求可压缩内容，但必须保留功能/场景判断、页面影响判断和待确认/拆回状态。

| 顺序 | 章节 | 说明 |
|---|---|---|
| 1 | 页面基本信息 | 明确页面名称、所属模块、页面目标和数据来源 |
| 2 | 页面入口 | 明确从哪里进入、由哪些上游页面或菜单触发 |
| 3 | 草图 / 对应原型 | 沟通阶段用 ASCII 草图表达页面结构；拆回正式 PRD 时在同一位置替换为 `对应原型` 链接 |
| 4 | 页面状态 | 明确空状态、有数据状态、加载状态和异常状态 |
| 5 | 字段与展示规则 | 明确筛选、列表、卡片、详情、表单、弹窗等展示内容和字段级校验 |
| 6 | 操作规则 | 按操作名称分别展开，明确所属区域、触发条件、执行动作、作用对象、校验规则、状态变化、页面和数据表现、去向/刷新策略、结果反馈和下游影响 |
| 7 | 异常与边界 | 明确空数据、无效数据、加载失败、权限不足等情况 |
| 8 | 页面弹窗 / 抽屉 | 按弹窗/抽屉分别展开，结构参考正式 PRD：基本信息、触发入口、字段与展示规则、操作规则、异常与边界、数据联动 |
| 9 | 权限相关行为 | 明确页面访问权限、按钮权限、数据范围受控点和无权限时的页面表现；具体角色映射引用 `系统管理.md` |
| 10 | 模块衔接 | 明确上游来源、下游流程、其他页面关系、操作留痕、回写、导出等关系 |
| 11 | 暂缓/待研发确认项 | 明确不在 MVP 或需研发确认的能力 |
| 12 | 页面待确认问题 | 只保留未确认项，已确认项应沉淀到对应规则章节 |

- 草案中的每条关键规则应标明状态或边界：`已确认`、`建议`、`待确认`、`待研发确认`、`暂缓`。
- 已确认规则不得长期留在“待确认问题清单”中；应移入对应主规则章节。
- 待确认问题必须是会影响页面结构、状态流转、权限、数据、异常处理或研发实现的关键问题。
- 每轮沟通后，应检查是否出现新增模块级通用规则；只有真正跨页面共用且必须唯一主定义的内容，才沉淀到对应模块下的“模块通用规则 / 跨页面共用规则”；页面触发规则优先回到具体页面章节，稳定后再拆回正式 PRD、对应目录 README 或专项规则文档。
- `权限相关行为` 章节只允许回答：是否需要页面访问权限、无页面权限时如何表现、无操作权限时按钮如何表现、数据范围是否受权限控制、详细角色配置见 `系统管理.md`。
- `业务使用对象/参与角色建议` 章节允许保留业务语义建议，但不得替代正式权限主定义，不得重复写角色权限矩阵或操作权限矩阵。

### 新页面需求对话输出模板
- 每次进入新页面需求沟通时，必须先在对话中按以下模板输出，不应直接写入过程文档。
- 用户确认 `Qx-y-1` 后，再继续 `Qx-y-2`；用户明确要求“更新文档”或“按建议”时，再把已确认内容落到过程文档。

```text
先讨论 Qx-y-1：页面目标和核心操作。

我的建议：

目标 | 说明
---|---
目标1 | 说明...
目标2 | 说明...
目标3 | 说明...

核心操作建议：
1. 操作1
2. 操作2
3. 操作3

待确认问题：
1. 问题1
2. 问题2
3. 问题3
```

- `目标` 应回答：页面为什么存在、服务谁、解决什么业务问题。
- `核心操作建议` 应回答：用户进入页面后主要做哪些动作。
- `待确认问题` 应只列影响后续结构、字段、状态、权限、异常或实现的关键问题。
- 对话输出阶段不强制包含完整 12 节；完整 12 节用于用户确认后沉淀到过程文档。

## 需求完备性检查清单
- 页面或功能确认前，必须按以下维度做完备性检查；发现缺口时，先补规则或列入待确认项，不直接标记已确认。

| 维度 | 必查问题 |
|---|---|
| 业务对象 | 当前页面操作的是任务、图片、标注对象、记录还是结果 |
| 角色粒度 | 不同角色处理粒度是否一致；不一致时如何映射 |
| 状态归属 | 状态属于任务、图片、人员结果还是最终结论 |
| 数据归属 | 草稿、无效、无可标注、记录分别挂在哪个对象下 |
| 触发时机 | 状态、记录、结果什么时候生成、更新、清除 |
| 多人冲突 | 多人结果不一致时是否覆盖，由谁裁决 |
| 上下游衔接 | 当前输出如何进入下一页面，是否去重、汇总、阻断 |
| 权限边界 | 谁能看、改、恢复、删除 |
| 异常边界 | 无数据、无效、删除、加载失败、待确认如何处理 |
| 追溯留痕 | 哪些操作留记录，记录字段和范围是什么 |
| MVP 边界 | 哪些做、哪些留入口、哪些待研发确认 |
| 草图一致 | 沟通阶段草图是否体现关键入口、状态、弹窗/抽屉；拆回正式 PRD 时是否替换为原型图链接并移除草图正文 |

- 完备性检查结果应体现在对应需求沟通文档的规则章节或待确认/待研发项中。
- 任务收尾答复必须说明：已检查维度、仍保留的待确认项、是否可进入下一页面。

## 执行约束
- 过程文档用于承接讨论，不长期承担业务规则主定义。
- 稳定结论应拆回最靠近判断逻辑的正式文档。
- 同一规则不得在多个文档重复完整展开。
- 任务完成前必须检查是否影响 PRD、原型、模板、流程图或归档记录。
