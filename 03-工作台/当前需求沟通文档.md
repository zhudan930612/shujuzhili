### 取舍与评审
- 推荐优先级：先做“标注任务与质检闭环”，而不是继续补周边管理功能。

| 候选方向 | 价值 | 当前问题 | 建议 |
|---|---|---|---|
| 标注任务与质检闭环 | 直接承接平台核心价值，决定照片能否变成训练数据 | 当前只有流程节点，没有任务分配、标注结果、质检裁决、驳回回流、待确认处理的页面规则 | 第一优先级 |
| 数据集/高质量数据池管理 | 承接 S6 和 AI 训练侧使用 | 依赖标注和质检结果，过早设计容易空转 | 第二优先级，跟在标注质检之后 |
| 报告生成/导出 | 更贴近保险公司交付 | 当前平台定位不是先做报告交付，且法规匹配、隐患识别结果尚未闭环 | 暂缓 |
| 行政区域字典后台维护 | 补强当前区域权限专题 | 系统管理已明确当前不新增独立行政区域管理页面，先按基础数据维护 | 暂缓，除非区域数据来源无法保障 |
| 隐患案例库页面 | 丰富知识库 | 知识库 PRD 已明确当前暂不展开案例库列表、录入、详情、导入页面 | 暂缓 |

- 评审意见：
  - 继续做采集前置功能的边际收益已经下降；真正卡住平台闭环的是采集后的治理处理。
  - 如果没有标注/质检模块，当前“数据治理平台”容易停在“项目与图片管理系统”，无法证明高质量数据池成立。
  - 标注质检必须与知识库回流一起设计；在新口径下，回流对象需要从“新隐患 / 规则缺失”扩展为“新物品类别 / 安全要素类别缺失 / 隐患规则缺失”。
  - 不建议先做 AI 训练或报告生成；训练侧需要稳定数据集，报告侧需要稳定识别结果和法规匹配结果，当前条件不足。
  - 口径变更风险：现有 [../01-产品架构/知识体系设计.md](../01-产品架构/知识体系设计.md) 与 [../02-PRD文档/后台管理/知识库管理.md](../02-PRD文档/后台管理/知识库管理.md) 当前以“隐患编码”为 AI 识别目标，若确认改为物品/安全要素标注，需要补充“物品/安全要素库”或调整知识体系层级，不能只改标注页面。

#### Q1 沟通记录：标注作业对象
- 待讨论点：
  - 第一版标注对象是否从“隐患”调整为“物品/安全要素”。
  - 物品/安全要素类别如何组织，例如安全帽、灭火器、脚手架、配电箱、防护栏、洞口盖板等。
  - 一张图片是否允许存在多个物品/安全要素标注框。
  - 是否还保留图片级“无目标/无可标注对象”结果，用于负样本或空样本沉淀。
  - 物品/安全要素标注结果如何与后续隐患判断、法规匹配和整改建议衔接。
  - 训练目标是否为目标检测模型训练，还是视觉大模型微调/样本学习。
- 初始评审：
  - 该调整有合理性：很多隐患判断依赖先识别现场对象及状态，例如先识别“安全帽”“灭火器”“脚手架”“防护栏”，再判断是否佩戴、是否缺失、是否过期、是否搭设异常。
  - 物品标注比隐患标注更接近视觉模型训练的基础任务，标注员理解成本通常低于直接判断复杂隐患，也更容易形成稳定样本。
  - 但这会改变当前知识体系：现有文档把“具体隐患编码”作为 AI 识别目标；若改为物品/安全要素标注，后续需要增加“物品/安全要素 -> 隐患规则 -> 法规/整改建议”的推理或匹配层。
  - 不能把“物品类别”直接塞进现有“隐患库”的四级具体隐患里，否则会混淆“对象是什么”和“问题是什么”两个概念。
  - “告知大模型什么是安全帽、灭火器、脚手架”需要进一步明确训练目标：是训练目标检测模型、微调视觉大模型，还是构建带框样本供后续模型评测。不同目标会影响导出格式和质量标准。
- 当前建议：
  - 第一版标注对象调整为“物品/安全要素”，不直接标注“隐患”。
  - 一张图片支持多个物品/安全要素框；每个框绑定一个物品/安全要素类别。
  - 物品/安全要素类别应独立建库或作为知识体系新增层，不与现有隐患库混放。
  - “无隐患”暂不作为标注标签；如图片中没有任何可标注物品/安全要素，记录为图片级“无可标注对象”。
  - 后续隐患判断通过“物品/安全要素识别结果 + 隐患判定规则/知识库”承接，不在本轮 Q1 中直接定义。
- 已确认结论：
  - 第一版训练目标为目标检测模型训练。
  - 标注任务需要框出物品/安全要素的位置，输出对象类别和坐标。
  - 标注对象为安全帽、灭火器、脚手架等物品/安全要素，不直接标注隐患。
  - 一张图片允许多个物品/安全要素框。
  - “无隐患”不作为标注标签；若图片无可标注物品/安全要素，记录为图片级“无可标注对象”。
  - 该结论后续需拆回知识体系与标注质检 PRD，并影响训练侧导出格式。

#### Q2 沟通记录：标注轮次与质检裁决
- 用户想法：
  - 不限制标注轮次。
  - 质检人员可以手动选择查看经过几个轮次的标注结果。
  - 质检人员基于查看结果决策是否进入高质量数据池。
- 初始评审：
  - 该思路适合目标检测训练数据治理：多轮标注可以沉淀不同人员对同一对象框和类别的判断差异，质检员再基于差异做最终裁决。
  - 相比固定 2 人或 3 人投票，可变轮次更灵活，适合早期类别标准还在校准的阶段。
  - 风险是如果完全不设流程边界，任务可能反复标注、质检成本失控，且“何时可以进入质检”不清晰。
  - 建议把“不限制轮次”理解为“业务上不固定必须几轮”，但系统仍需要记录轮次、标注人、时间、版本、标注结果和质检裁决，避免结果不可追溯。
- 当前建议：
  - 标注任务支持多轮标注，不强制固定为 2 人或 3 人。
  - 每轮标注结果独立留痕，不覆盖上一轮结果。
  - 质检工作台支持查看：最新一轮、指定轮次、全部轮次对比。
  - 质检员可选择某一轮结果作为基础进行修正，也可直接重新绘制标准结果。
  - 质检裁决结果包括：进入高质量数据池、退回继续标注、不入池。
  - 进入高质量数据池时，以质检员确认的“标准框 + 标准类别”为最终入池结果，不直接以某个标注员原始结果入池。
  - 系统应显示轮次差异，例如同一对象类别不一致、框位置偏差明显、漏框/多框，但差异算法可作为辅助，不替代质检员裁决。
- 已确认结论：
  - 标注任务支持多轮标注，不强制固定为 2 人或 3 人。
  - 每轮标注结果独立留痕，不覆盖上一轮结果。
  - 质检工作台支持查看最新一轮、指定轮次和全部轮次对比。
  - 质检员可选择某一轮结果作为基础进行修正，也可重新绘制标准结果。
  - 质检裁决结果包括：进入高质量数据池、退回继续标注、不入池。
  - 进入高质量数据池时，以质检员确认的“标准框 + 标准类别”为最终入池结果，不直接以某个标注员原始结果入池。
  - 系统可辅助显示轮次差异，例如类别不一致、框位置偏差明显、漏框/多框，但差异算法不替代质检员裁决。

#### Q3 沟通记录：质检范围与标准结果生成
- 待讨论点：
  - 质检工作台按图片组织，还是按单个对象框组织。
  - 质检员在裁决阶段是否只能选择某个标注员/某一轮的结果。
  - 质检员是否允许自行新增、修改、删除标注框，并调整对象类别。
- 初始评审：
  - 如果质检员只能选择既有标注结果，最终标准结果会被已有标注质量限制；遇到所有标注员都漏框、框偏差都较大、类别都错时，只能退回，效率低。
  - 目标检测训练需要高质量标准框，质检员应被定义为最终标准结果的责任人，而不只是投票选择人。
  - 但允许质检员自行标注会增加权限和留痕要求：必须记录质检员新增、修改、删除了哪些框，避免无法追溯。
  - 不建议把“选择某个人的一整轮结果”作为唯一裁决方式；现实中同一张图可能 A 的第 1 个框准，B 的第 2 个框准，质检员还需要补一个漏掉的框。
- 当前建议：
  - 质检任务以图片为主任务单位，进入详情后按对象框生成最终标准结果。
  - 质检员可以选择某一轮/某个标注员的框作为基础。
  - 质检员可以从不同轮次、不同标注员中选取不同对象框组合成标准结果。
  - 质检员可以自行新增框、调整框坐标、修改对象类别、删除错误框。

#### Q4A 沟通记录：标注要素类别库
- 讨论目标：
  - 明确安全帽、脚手架、灭火器等标注选项的主定义位置。
  - 明确类别库字段、属性字段、维护规则和与隐患库的边界。
- 初始评审：
  - 标注要素类别库是目标检测训练的类别字典，直接决定模型输出类别和数据集导出类别映射。
  - 该库必须独立于现有隐患库；隐患库描述“问题是什么”，标注要素类别库描述“对象是什么”。
  - 用户补充的“灭火器有正常/损坏，安全帽有白帽子/红帽子”等不应拆成大量对象类别；更适合作为对象类别下的属性。
  - MVP 不区分“属性名称”和“属性值”；类别下直接维护多个属性名称，例如 `安全帽 -> 白色、红色`，`灭火器 -> 正常、损坏`。
  - 类别不能随意改名或删除，否则历史标注结果和训练数据集会失去稳定映射。
  - 属性会增加标注复杂度，MVP 不宜做成通用无限属性系统；建议只支持领域工程师为单个类别配置少量枚举属性。
- 当前建议：
  - MVP 建立独立“物品/安全要素类别库”，由领域工程师维护。
  - MVP 不强制类别组层级，先采用平铺类别项列表。
  - 类别项示例：安全帽、反光背心、安全带、灭火器、消防栓、脚手架、脚手板、防护栏杆、洞口盖板、配电箱、电缆线、警示牌。
  - MVP 必填字段建议：类别名称、状态；系统需生成稳定类别ID。
  - 每个类别至少配置一个属性。
  - 若某个类别 MVP 阶段暂不需要细分属性，也应配置一个默认属性名称，例如 `通用`、`未区分` 或 `默认`，用于承接标注选择。
  - MVP 支持类别属性配置，属性为可选枚举项，不支持自由文本属性。
  - 属性配置示例：
    - 灭火器：正常、损坏。
    - 安全帽：白色、红色、黄色、蓝色。
  - 标注员框选对象并选择类别后，必须继续选择该类别下的属性名称。
  - 属性名称由领域工程师维护；MVP 不允许标注员自由新增属性名称。
  - 暂缓字段：类别组、适用行业域、正例说明、反例说明、版本号、复杂多级属性。
  - 类别项允许停用，不允许物理删除；历史标注继续保留原类别ID。
  - 标注下拉只展示启用类别；历史记录和数据集导出可显示停用类别。
- 已确认结论：
  - MVP 采用独立“物品/安全要素类别库”，由领域工程师维护，不混入现有隐患库。
  - MVP 暂不做类别组，采用平铺类别项列表。
  - 类别项必须有唯一且不可变的数据库内部编码，用于训练导出、历史标注映射和系统识别。
  - MVP 不在用户端展示或填写类别编码。
  - 用户端类别项基础字段包括：类别名称、状态。
  - 每个类别至少配置一个属性。
  - 标注员框选对象并选择类别后，必须继续选择该类别下的属性名称。
  - 若某个类别 MVP 阶段暂不需要细分属性，也应配置一个默认属性名称，例如 `通用`、`未区分` 或 `默认`。
  - 类别项允许停用，不允许物理删除；历史标注继续保留原类别ID。
  - 标注下拉只展示启用类别；历史记录和数据集导出可显示停用类别。

##### Q4A 字段及规则草案

###### 1. 列表字段

| 字段 | 展示规则 | 说明 |
|---|---|---|
| 类别名称 | 展示类别中文名称 | 如安全帽、灭火器、脚手架 |
| 属性名称 | 直接平铺展示该类别下配置的属性名称 | 如 `白色、红色、黄色`；`正常、损坏` |
| 状态 | 展示启用/停用 | 启用类别可用于新标注；停用类别仅用于历史展示和导出追溯 |
| 操作 | 展示可用操作 | 查看、编辑、停用/启用 |

列表不展示数据库内部编码；不展示创建人、创建时间、更新人、更新时间。

###### 2. 类别项字段

| 字段 | 必填 | 规则 | 示例 |
|---|---|---|---|
| 类别内部编码 | 数据库生成 | 全局唯一；创建后不可修改；用户端不展示、不填写；用于训练导出、历史标注映射和系统识别 | - |
| 类别名称 | 是 | 展示给领域工程师、标注员、质检员的中文名称；允许修改，但不得改变内部编码 | 安全帽、灭火器、脚手架 |
| 状态 | 是 | 枚举：启用、停用；启用类别可用于新标注，停用类别仅用于历史展示和导出追溯 | 启用 |

###### 3. 属性字段

| 字段 | 必填 | 规则 | 示例 |
|---|---|---|---|
| 所属类别 | 是 | 属性必须归属于一个类别；每个类别至少配置一个属性 | 安全帽 |
| 属性名称 | 是 | 类别下的可选属性；同一类别下属性名称不可重复；标注员只能从领域工程师维护的属性名称中选择，不允许自由输入 | 白色、红色、正常、损坏 |
| 属性状态 | 是 | 枚举：启用、停用；启用属性可用于新标注，停用属性仅用于历史追溯 | 启用 |
| 上传图片 | 否 | 挂在单个属性下；可不上传；如上传，每个属性最多 3 张 | 白色安全帽图片 |

###### 4. 维护规则

| 规则项 | 规则 |
|---|---|
| 维护角色 | 仅领域工程师维护类别、属性和属性图片 |
| 类别结构 | MVP 采用平铺类别项列表，暂不做类别组 |
| 类别稳定标识 | 数据库生成内部编码，创建后不可修改；用户端不展示、不填写；如类别名称调整，内部编码仍保持不变 |
| 属性要求 | 每个类别至少配置一个属性；如果暂不需要细分，配置默认属性名称，如 `通用`、`未区分` 或 `默认` |
| 属性唯一性 | 同一类别下属性名称不可重复；不同类别下可存在相同属性名称，如安全帽/红色与警示牌/红色 |
| 属性图片 | 图片挂在属性下，不挂在类别下；每个属性最多 3 张；可不上传 |
| 属性状态 | 属性支持启用/停用；启用属性可用于新标注，停用属性仅用于历史展示和导出追溯 |
| 删除规则 | 类别和属性不允许物理删除，仅允许停用 |
| 标注可选范围 | 标注下拉只展示启用类别和启用属性 |
| 历史追溯 | 历史标注继续保留原类别内部编码和属性名称；停用后不影响历史展示与导出 |
| 待确认类别 | 标注员遇到缺失类别时选择 `待确认类别` 并填写备注说明，不直接新增正式类别 |

###### 5. 标注使用规则

| 场景 | 规则 |
|---|---|
| 正常标注 | 标注员框选对象后，必须选择类别和该类别下的属性名称 |
| 类别无可选属性 | 不允许进入标注；类别发布前必须至少配置一个启用属性 |
| 属性无法判断 | MVP 阶段可通过领域工程师配置 `未区分` 属性承接，标注员不得自由输入属性 |
| 类别缺失 | 选择 `待确认类别`，并手动输入备注说明 |
| 入池要求 | 入高质量数据池的标准结果必须有正式类别和正式属性；`待确认类别` 不可直接入池 |
