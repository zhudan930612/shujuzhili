# 后台管理原型规范

## 目录定位
当前目录用于存放后台管理系统的页面原型文件。后台原型先按页面上下文组织，再在页面内部表达不同状态。

## 主要内容
- `*.html`：后台管理页面原型。
- [assets/](assets/)：后台原型公共样式、公共交互和组件契约。
- [模板文件/](模板文件/)：后台页面直接配套的 Excel 模板、示例附件。
- [后台管理-组件预览.html](后台管理-组件预览.html)：后台公共组件组合示例。

## 相关入口
- 后台 PRD：[../../02-PRD文档/后台管理/](../../02-PRD文档/后台管理/)
- 公共组件说明：[assets/README.md](assets/README.md)

## 文件组织规则
- 后台原型按页面上下文组织，而不是按弹窗类型组织。
- 默认采用 `一页一文件`：列表页、详情页、上传页、字典管理页等各自对应一个 HTML。
- 同一页面触发的弹窗、确认框、阻断提示、特殊模式，优先并入该页面 HTML 内展示。
- 只有本身就是独立页面流程的内容，才适合单独形成一个 HTML 文件。

## 归位规则
- 页面级原型直接放在当前目录。
- 公共样式、公共脚本和可复用组件契约放在 [assets/](assets/)。
- 模板、示例文件等附件放在 [模板文件/](模板文件/)。
- 移动端原型不放在当前目录，统一放在 [../移动端/](../移动端/)。

## 维护约定
- 修改后台原型前，先查看 [assets/README.md](assets/README.md) 和 [后台管理-组件预览.html](后台管理-组件预览.html)。
- 已有公共组件能覆盖时，优先复用公共组件，不新增页面私有平行实现。
- 当前目录只承载视觉和交互表达，业务规则主定义仍以 [../../02-PRD文档/后台管理/](../../02-PRD文档/后台管理/) 为准。

## 视觉基线
- 为本项目生成后台管理系统的 HTML / SVG 原型效果图时，默认使用当前已确认的蓝白后台风格，不随意切换视觉体系。
- 整体结构：`顶部深蓝导航 + 左侧白色菜单 + 中部浅灰工作区 + 白色内容卡片`。
- 顶部导航：深蓝渐变、白字、一级功能横向排列、右上角用户信息。
- 左侧菜单：白底菜单，当前模块蓝底高亮。
- 内容区：默认包含面包屑、页签/模块标题、筛选区、列表卡片、表格、分页。
- 默认桌面后台画布：`1920 × 1080 px`。

## 风格约束
- 表格、筛选器、按钮、分页等组件应偏业务系统风格，强调规整、稳定、清晰。
- 禁止做营销页、站点页、海报页式设计。
- 真实界面内容与功能说明必须分层；如需展示说明，优先用抽屉、浮窗、侧边说明板，不把说明塞进界面主体。
- 配色、间距、控件风格应优先延续用户已确认的参考图气质，保证同一项目风格统一。

## 组件优先原则
- 生成或修改 `04-原型效果图/后台管理/` 下的原型页面时，必须优先复用已有公共组件。
- 处理后台原型页时，优先使用 `$prototype-component-first` 技能，并按该技能定义的“组件优先”工作流执行。
- 生成原型前，优先检查并复用以下公共组件来源：
  - [assets/prototype.css](assets/prototype.css)
  - [assets/prototype.js](assets/prototype.js)
  - [assets/README.md](assets/README.md)
  - [后台管理-组件预览.html](后台管理-组件预览.html)
- 已有组件能够满足需求时，禁止重复手写同类 UI、页面私有样式或平行实现。
- 如遇到现有组件无法覆盖的新通用结构，应先沉淀为公共组件，再接入具体页面。
- 页面级私有实现只允许用于明显业务特化、且确认不具备复用价值的内容。

## 原型修改前检查清单
1. 先查看 [assets/README.md](assets/README.md)，确认是否已有对应组件。
2. 再查看 [后台管理-组件预览.html](后台管理-组件预览.html)，确认是否已有完整组合示例。
3. 先写出“页面元素 → 组件名”的映射，再开始修改页面。
4. 若页面存在以下结构，必须优先复用对应组件：
   - 列表骨架：`proto-list-shell`
   - 列表工具区：`proto-list-tools`
   - 导出能力：`导出选项 + 导出按钮` 组合整体接入
   - 页面底部操作栏：`page-actions`
   - 操作列：`proto-row-actions`
5. 若组件已覆盖，禁止改为页面私有平行实现。

## 组件优先执行顺序
1. 查看 [../../AGENTS.md](../../AGENTS.md) 中顶层规则。
2. 查看 [assets/README.md](assets/README.md) 中组件清单与最小结构。
3. 查看 [后台管理-组件预览.html](后台管理-组件预览.html) 中完整示例。
4. 列出本页组件映射。
5. 仅在组件不足时，才允许新增页面私有实现，并注明原因。

## 高频误区补充
- 列表导出不等于单个“导出”按钮；若组件预览存在导出组合，必须整体复用，不得只取其中一部分。
- 阻断态、空态、编辑受限态等特殊状态，按钮位置仍需服从共享布局规则；不能因为状态特殊，就把按钮塞回标题区、图片区或局部区块。

## 参考图执行规则
- 当用户提供参考图片时，必须将参考图视为唯一视觉基准，禁止擅自“优化”或“推断”。
- 先严格复刻结构、层级、布局关系，不做“我觉得更好”的调整。
- 只有用户明确要求“优化 / 重设计 / 换风格”时，才允许设计发挥。
- 如果参考图与文档冲突，先指出冲突点，不自行脑补。
- 执行顺序固定为：`先复刻 → 有明确优化指令才调整 → 有冲突先确认再执行`。

## 同一 HTML 的推荐结构
1. 页面骨架
2. 一级状态切换
3. 每个主状态下的页面主体
4. 必要时在主状态内再加二级切换
5. 弹窗覆盖层始终叠加在所属页面上

## 推荐实现方式
- 使用 `data-view-scope` 作为状态切换作用域。
- 使用 `state-button` 作为一级或二级状态切换按钮。
- 使用 `data-view-panel` 承载不同状态面板。
- 弹窗继续使用 `modal-stage`、`modal` 等已有结构，但展示上依附于所属页面。

## 状态分层规则
- 一级状态：页面主状态，例如空状态、详情状态、编辑状态、批量管理态。
- 二级状态：当前主状态下的关键交互态，例如删除确认、保存确认、阻断提示。
- 轻量差异：不单独切状态，例如按钮禁用、文案差异、数量变化、轻量校验提示。

## 示例
### 上传巡查记录页
- 一级状态：空状态 / 已上传状态 / 修改状态
- 二级状态：删除确认弹窗 / 保存确认弹窗 / 阻断提示
- 表达方式：先切换页面主体，再在当前主体上叠加弹窗或阻断提示

### 字典管理页
- 一级状态：页面态 / 新增弹窗 / 编辑弹窗 / 详情弹窗
- 二级状态：不同字典类型在同类弹窗中的子态切换
- 表达方式：页面主体保持稳定，弹窗态和字典类型子态通过页内按钮切换展示
