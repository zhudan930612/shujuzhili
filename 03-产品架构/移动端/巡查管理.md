# 巡查管理

## 文档定位
- 本文档是移动端巡查管理模块的主 PRD，承接该模块的页面设计、共享规则和跨页面数据流。
- 原型继续按独立页面 HTML 维护；本文档按模块整合页面规则，不再单独维护页面级 md。
- 历史迁移来源主要为 `docs/90-决策归档/2026-03-28-流程图决策.md`。

## 模块定位
- 本模块负责移动端巡查采集链路，是巡查员在 App 端完成登录、项目选择、图片上传、巡查历史查看的核心模块。
- 数据治理闭环流程以 [../../02-业务流程.mmd](../../02-业务流程.mmd) 为准。

## 模块边界
- 承接登录、项目列表、搜索、项目详情、待上传记录、我的、巡查记录和巡查详情。
- 后台巡查记录管理、删图管理和知识库维护不在本模块展开。

## 通用规则
### App 端功能极简
- App 只做三件事：进入项目、选择图片、批量上传；不做现场隐患标注或法规填写。
- 信息后置到后台标注链路，避免巡查员现场判断污染数据。

### 照片必须与项目关联
- 所有照片必须关联到具体项目。
- 支持扫码、项目列表选择、事后补录三种方式，以保证采集链路不断裂。
- 一次进入项目后，批量上传自动继承项目 ID。

### 巡查记录生成规则
| 规则项 | 说明 |
|--------|------|
| 生成条件 | 当前上传会话内至少 1 张图片成功上传，即生成 1 条巡查记录 |
| 会话边界 | 同一上传会话内的失败重传补入原记录，不生成新记录 |
| 草稿处理 | 草稿仅表示未完成会话，不生成巡查记录 |
| 项目状态联动 | 项目是否已巡查取决于是否存在巡查记录 |

### 图片水印方案（待确认）
- 当前仍保留为待确认规则项。
- 如保险公司要求可见水印，再在 App 强制拍照方案和导出时加水印方案中二选一。

## 页面设计


### 登录页


###### 对应原型
- 暂无独立原型文件，后续新增原型时统一放入 docs/06-原型效果图/App/。
###### 设计内容
**决策结论**：登录页面以手机号验证码登录为主，不提供第三方快捷登录。

**用户权限规则**：
- 允许登录的账户必须在后台管理系统中已创建
- 未在后台创建的手机号，即使验证码正确也提示"无权限查看"或类似提示
- 后台管理员可提前导入巡查员手机号，或运营手动创建账号

**登录页设计**：

```
┌─────────────────────────────┐
│                             │
│                             │
│          ┌─────┐            │
│          │ LOGO │           │  ← 平台Logo
│          └─────┘            │
│                             │
│      数据治理巡查平台        │
│                             │
│                             │
│  ┌─────────────────────┐   │
│  │ 📱  请输入手机号     │   │  ← 手机号输入框
│  └─────────────────────┘   │
│                             │
│  ┌─────────────────────┐   │
│  │ 🔢  验证码    [获取] │   │  ← 验证码输入 + 获取按钮
│  └─────────────────────┘   │
│                             │
│  ☑️ 已阅读并同意《用户服务协议》│  ← 勾选后才能登录
│           和《隐私政策》         │
│                             │
│       [  登 录  ]           │  ← 登录按钮（验证码正确+账号有权限+已勾选协议）
│                             │
│                             │
│                             │
└─────────────────────────────┘
```

**功能说明**：

| 元素 | 交互 | 说明 |
|------|------|------|
| 手机号输入 | 11位数字校验 | 输入完成后启用"获取验证码"按钮 |
| 获取验证码 | 点击后60秒倒计时 | 发送短信验证码到手机 |
| 协议勾选 | 必须勾选才能登录 | 点击文字可跳转查看《用户服务协议》和《隐私政策》全文 |
| 登录按钮 | 校验验证码+后台权限+协议勾选 | 三者都满足才可登录，否则提示相应错误 |


**协议相关说明**：
- 首次登录必须勾选同意协议，勾选状态在 App 本地存储
- 协议内容更新时，下次登录需重新确认
- 未勾选协议时点击登录，提示"请先阅读并同意用户协议"

**无权限提示**：
- 当手机号验证码正确但未在后台创建时，提示："您暂无巡查权限，请联系管理员添加账号"
- 引导用户联系平台运营人员

|------|------|

| 下拉刷新 | 不支持 |


**状态显示规则**：

| 状态 | 展示方式 | 说明 |
|------|---------|------|
| **待上传** | 项目卡片右上角红色数字角标，显示待上传总数（如"3"） | 数量 = 草稿数 + 失败数，与项目详情页待上传卡片数量一致 |
| **未巡查** | 🔴 红色"未巡查"标签，视觉上优先突出 | 无待上传数据时显示 |
| **已巡查** | 🟢 绿色标签，显示巡查人+巡查时间 | 无待上传数据时显示 |

**待上传角标样式说明**：

| 属性 | 说明 |
|------|------|
| **位置** | 项目卡片右上角 |
| **样式** | 红色圆形或圆角矩形，白色数字 |
| **数字** | 显示待上传总数（草稿 + 失败）|
| **显隐** | 有待上传数据时显示，无数据时隐藏 |
| **优先级** | 高于"未巡查"/"已巡查"状态，有角标时状态标签正常显示 |

**角标与状态标签的共存规则**：

| 场景 | 显示效果 |
|------|---------|
| 有待上传 + 未巡查 | 🔴 未巡查（标签）+ 右上角红色数字角标 |
| 有待上传 + 已巡查 | 🟢 已巡查（标签）+ 右上角红色数字角标 |
| 无待上传 + 未巡查 | 🔴 未巡查（标签），无角标 |
| 无待上传 + 已巡查 | 🟢 已巡查（标签），无角标 |

**示例布局**：

```
┌─────────────────────────────┐
│ ┌───────────────────────┐   │
│ │ 🔴 未巡查        ┌─┐  │   │  ← 红色角标在右上角
│ │  华润城三期      │3│  │   │     显示待上传数量
│ │  📍 南山区XX路   └─┘  │   │
│ │  🗓️ 2026.01.20 - 2026.04.30 │
│ │  👷 王工  📞 138****1234   │
│ └───────────────────────┘   │
└─────────────────────────────┘
```

**排序规则**：

| 优先级 | 排序维度 | 规则 |
|--------|---------|------|
| 第一 | 巡查状态 | 未巡查项目排在前，已巡查排在后 |
| 第二 | 施工时间 | **按施工开始时间正序，越早开工越靠前**（先开工先巡查） |
| 第三 | 创建时间 | 相同状态下，按项目创建时间正序 |

**示例排序结果**：
```
1. 🔴 未巡查 - 华润三期（2026.01.20开工，最早需优先巡查）
2. 🔴 未巡查 - 前海时代（2026.02.15开工）
3. 🔴 未巡查 - 万科云城（2026.03.01开工，最新开工）
4. 🟢 已巡查 - 中海锦城（2026.02.01开工，上周巡查）
5. 🟢 已巡查 - 招商花园（2026.03.10开工，昨日巡查）
```

**特殊情况**：
- 搜索状态下：按搜索结果相关度排序，状态优先级降为第二维度
- 筛选"已巡查"时：按最近巡查时间倒序，最近巡查的排前面

**关键设计点**：
- 一个项目支持多次巡查，列表页显示最近一次巡查信息
- 未巡查项目视觉上优先突出（红色标签），便于巡查员识别
- 点击项目卡片进入项目详情页
- **点击卡片中的电话号码可直接拨打**（调用系统拨号能力）

**时间轴设计说明**：

| 元素 | 说明 |
|------|------|
| **● 日期节点** | 实心圆点标记日期，同一天的多条记录共享一个日期节点 |

**时间轴样式规则**：

| 场景 | 展示方式 |
|------|---------|
| **不同日期** | 新的●日期节点，与前一条记录有明显间距 |
| **同一天多次** | 共享日期，用│连接，下方以○标记具体时间 |
| **最新记录** | 最上方，●节点可高亮（如蓝色或加粗）|
| **历史记录** | 正常显示，按时间倒序排列 |

**排序规则**：按巡查时间**倒序排列**（最新的巡查记录在最上面）。

**巡查记录判定规则**：

巡查记录以**完整上传会话**为粒度进行区分，具体规则如下：

| 规则项 | 说明 |
|--------|------|
| **会话开始时机** | 用户从项目详情页发起一次新的上传操作，且当前项目下不存在草稿或失败记录 |
| **记录创建条件** | 当前上传会话内至少1张图片成功上传，即生成一条巡查记录 |
| **同一项目多次巡查** | 同一项目可有多次独立巡查；仅当前一上传会话已完成或被清空后，下一次上传才生成新记录 |
| **失败重传处理** | 同一会话内如部分图片上传失败，失败图片后续重传成功时补入原巡查记录，不生成新记录 |
| **草稿处理** | 草稿仅表示未完成会话，不生成巡查记录；草稿后续上传成功时归入当前会话对应的巡查记录 |

**场景示例**：
- 场景1：巡查员A对项目X进行巡查，一次性上传15张图片全部成功 → 生成1条巡查记录（15张）
- 场景2：巡查员A对项目X巡查，选择20张图片上传，因网络问题仅10张成功 → 先生成1条巡查记录；剩余10张稍后在待上传页重传成功 → 补入原巡查记录，不新增记录
- 场景3：巡查员A周一巡查项目X上传8张，周三再次巡查同一项目上传12张 → 生成2条独立巡查记录

**设计理由**：
- 保持“一次巡查 = 一次完整上传会话”的用户心智，避免同一次巡查被拆成多条记录
- 网络不稳定场景下，成功数据可先入库，失败图片后续补齐，不影响巡查次数统计
- 草稿、失败、重传都围绕同一未完成会话处理，业务边界更清晰

**边界情况处理**：
| 场景 | 处理 |
|------|------|
| 图片数量多（>30张） | 前端分页加载或虚拟滚动，仍保持平铺展示 |
| 想查看某次特定巡查的图片 | 点击下方"巡查记录"列表，进入该批次详情页 |



**项目删除后的处理**：

当用户已进入项目详情页或待上传记录页，后台删除该项目后：

| 用户操作 | 提示 |
|----------|------|
| 点击上传/保存/任何与后台交互的操作 | Toast提示"项目已不存在，无法操作" |
| 点击返回 | 正常返回列表页，列表刷新后该项目消失 |


**上传前自动压缩策略（仅适用于App 端）**：

| 原图大小 | 处理方式 | 说明 |
|---------|---------|------|
| ≤5MB | 原图直接上传 | 保证清晰度 |
| >5MB | 自动压缩至5MB以内 | 质量压缩80%，保持分辨率，用户无感知 |

**压缩对AI训练的影响（仅适用于App 端）**：适度压缩（质量≥80%）不影响隐患识别，因为AI依赖的是边缘特征而非像素级精度。

**失败处理机制**：

| 失败原因 | 处理策略 |
|---------|---------|
| 网络异常 | 自动重试3次，仍失败则标记"待上传"存本地，用户可手动触发重新上传 |

**图片规格与并发策略**：

| 配置项 | 建议值 | 说明 |
|--------|--------|------|
| **并发上传数** | 3张 | 固定并发，平衡速度与稳定性 |
| **超时时间** | 30秒/张 | 超时时自动重试或标记失败 |


**图片格式限制**：

| 限制项 | 规则 |
|--------|------|
| **支持格式** | JPG、PNG |
| **不支持** | HEIC、GIF、视频等 |
| **尺寸要求** | 无限制 |

##### 待上传记录页

**页面用途**：统一处理两种场景的图片上传操作：
1. **相册选择后进入**：选择图片后进入此页，可预览、删除、追加后上传
2. **从项目详情页进入**：点击"待上传卡片"进入，处理已保存的草稿或失败的图片

**上传会话规则**：

- 待上传记录页承载当前项目的**未完成上传会话**
- 项目下只要存在草稿或失败记录，就不能从项目详情页直接再次进入相册开启新会话
- 用户必须先在待上传记录页完成当前会话：
  - 上传成功并清空待上传
  - 或手动删除/清空待上传记录
- 只有当前会话结束后，才允许从项目详情页再次发起新的上传会话

**继续添加规则**：

| 页面状态 | 处理方式 |
|------|---------|
| **仅有草稿** | 允许点击 `继续添加`，新选择的图片并入当前会话 |
| **出现失败记录** | 进入失败处理模式，隐藏 `继续添加`，用户先处理失败图片 |

**草稿保存机制**：

用户从相册选择图片进入待上传记录页后，**返回时弹出确认框**：

```
┌─────────────────────────────┐
│                             │
│       是否保存为草稿？       │
│                             │
│    当前有 5 张图片未上传     │
│                             │
│   ┌─────────┬─────────┐    │
│   │  不保存  │   保存   │    │
│   └─────────┴─────────┘    │
│                             │
└─────────────────────────────┘
```

| 用户选择 | 处理 |
|---------|------|
| **保存** | 图片保存为"草稿"状态，关联到该项目，下次进入待上传记录页可见 |
| **不保存** | 清除本次选择的图片，返回项目详情页，不保存任何数据 |

**两种数据状态**：

| 状态 | 说明 | 来源 |
|------|------|------|
| **草稿** | 已保存但未上传的图片 | 用户选择后点击"保存" |
| **失败** | 上传失败需重试的图片 | 上传过程中网络异常导致 |

**数据有效期与清理策略**：

| 策略 | 规则 |
|------|------|
| **有效期** | 永久保存，不自动清理 |
| **存储上限** | 不限制 |
| **存储位置** | App 本地存储（按**手机号+项目ID**隔离）|
| **手动清理** | 在「我的」页面提供「清理缓存」入口，可一键清除当前用户的所有草稿和失败记录 |

**退出登录处理**：
- 退出时不自动清理数据，仅提示用户数据会保留
- 数据与手机号绑定，同账号下次登录仍可见
- 换账号登录时数据自动隔离（不同账号互不干扰）

**多账号数据隔离说明**：

缓存数据与**登录手机号**绑定，实现多巡查员共用设备时的数据隔离：

| 场景 | 处理方式 |
|------|---------|
| **巡查员A登录** | 只显示A手机号关联的草稿和失败记录 |
| **A退出，B登录** | 自动切换为B的数据，A的数据不可见 |
| **B退出，A重新登录** | 恢复显示A的历史数据 |

**存储Key设计示例**：
```
{phone}_{projectId}_drafts   // 草稿图片
{phone}_{projectId}_failed   // 失败图片
```

**清理逻辑**：
- 退出登录时，仅询问是否清理**当前用户**的待上传数据
- 清理操作只删除当前手机号关联的数据，不影响其他用户
- 换设备登录时，由于数据存在本地，新设备看不到历史草稿

**时间轴设计说明**：

| 元素 | 说明 |
|------|------|
| **● 日期节点** | 实心圆点标记日期，同一天的多条记录共享一个日期节点 |
| **│ 时间线** | 竖线连接同一天内的多次巡查记录 |
| **时间** | 精确到分钟，显示在日期下方 |
| **项目信息** | 缩进显示，包含项目名称、地址、图片数量 |
| **同一天多次巡查** | 以空心圆○标记，缩进对齐显示 |

**时间轴样式规则**：

| 场景 | 展示方式 |
|------|---------|
| **不同日期** | 新的●日期节点，与前一条记录有明显间距 |
| **同一天多次** | 共享日期，用│连接，下方以○标记具体时间 |
| **最新记录** | 最上方，●节点可高亮（如蓝色或加粗）|
| **历史记录** | 正常显示，按时间倒序排列 |

**排序规则**：按巡查时间**倒序排列**（最新的巡查记录在最上面）。

**巡查记录判定规则**：

巡查记录以**完整上传会话**为粒度进行区分，具体规则如下：

| 规则项 | 说明 |
|--------|------|
| **会话开始时机** | 用户从项目详情页发起一次新的上传操作，且当前项目下不存在草稿或失败记录 |
| **记录创建条件** | 当前上传会话内至少1张图片成功上传，即生成一条巡查记录 |
| **同一项目多次巡查** | 同一项目可有多次独立巡查；仅当前一上传会话已完成或被清空后，下一次上传才生成新记录 |
| **失败重传处理** | 同一会话内如部分图片上传失败，失败图片后续重传成功时补入原巡查记录，不生成新记录 |
| **草稿处理** | 草稿仅表示未完成会话，不生成巡查记录；草稿后续上传成功时归入当前会话对应的巡查记录 |

**场景示例**：
- 场景1：巡查员A对项目X进行巡查，一次性上传15张图片全部成功 → 生成1条巡查记录（15张）
- 场景2：巡查员A对项目X巡查，选择20张图片上传，因网络问题仅10张成功 → 先生成1条巡查记录；剩余10张稍后在待上传页重传成功 → 补入原巡查记录，不新增记录
- 场景3：巡查员A周一巡查项目X上传8张，周三再次巡查同一项目上传12张 → 生成2条独立巡查记录

**设计理由**：
- 保持“一次巡查 = 一次完整上传会话”的用户心智，避免同一次巡查被拆成多条记录
- 网络不稳定场景下，成功数据可先入库，失败图片后续补齐，不影响巡查次数统计
- 草稿、失败、重传都围绕同一未完成会话处理，业务边界更清晰

## 跨页面状态与数据流
- 登录成功后进入项目列表；从项目列表进入项目详情，再发起上传会话。
- 项目详情页、待上传记录页、巡查记录页围绕同一项目或同一上传会话进行状态回流。
- 待上传图片、草稿、失败记录都按“手机号 + 项目 ID”在移动端本地隔离。

## 异常与边界
- 无权限手机号即使验证码正确也不得进入系统。
- 失败图片优先在待上传记录页处理，未完成会话时禁止直接开启新的上传会话。
- 巡查记录展示按完整上传会话建模，不按单张图片拆分。
